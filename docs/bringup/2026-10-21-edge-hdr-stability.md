# 2026-10-21：7.x HDR 切换与稳定性验收

继续 [HDR 高光与连接优化](2026-10-20-edge-hdr-optimization.md)，修复后台模式切换期间
输入通知造成的重复切换，并验证显示休眠和真实 HDMI 拔插。整机休眠因用户暂不方便操作
而取消等待，不能用显示休眠结果代替。内核、EDID、HDR 曲线和 5.15 默认启动项未改。

## 事件顺序修复

最终 One-KVM 为 `edc426a17e7d5036b2c33b588dca993d79a8d90c`，独立 ELF SHA256
`9a5094e2587abfa5cac27b622190243e0e09a9ca5315f6b3263df69e782f54b5`。
Linux 仍为 `c4e982bf80cd0cc8b2f988fd2f6de34017a1838c`，模块、设备树及私有插件未替换。

前版 One-KVM `6e1910f8` 的普通输入通知保护依赖 `videoRestarting=false`。
`stream.mode_switching` 已把它设为 true，但后台尚未发 `mode_ready` 时，输入发现仍可
到达；此时健康的 peer 会被再次关闭，并重新请求模式切换。受控浏览器事件复现：
旧版 SSRC `1070902297→2768294349`，加上后台切换保护后保持 `1531476960`。

新逻辑在“无 transition ID、后台正在切换、peer 已连接”时让原切换完成，同时消费
已处理的恢复标志，防止它误吞下一次用户主动改配置。两条事件顺序都运行实际 Vue
处理函数回归：前者旧版会重复切换，后者若不消费标志会遗漏后续请求；修复后均通过。
另修正保留 peer 后的加载层及旧帧遮罩：`mode_ready` 与当前 WebRTC 模式相符且已连接时结束加载，
不等待不会再发生的 connected 状态变化；断线、其他编码和 MJPEG 继续等待各自的首帧。
断线、显式配置、MJPEG 与本地模式切换的恢复路径保留。

另复现初始 HTTP 状态与实时事件的竞态：把查询中的旧 busy 响应延迟到新 streaming
事件之后，旧版会遮住正在解码的画面，后续输入通知又令 SSRC `194010803→1635623011`。
启动查询现在记录状态版本，若期间收到更新的实时事件则不再覆盖；没有实时事件时
仍正常使用查询结果。回归同时覆盖新 streaming/no_signal 优先与正常初始 busy 查询。

历史上单次初始切换重连没有完整事件轨迹，不能断言就是上述哪条竞态。此次先在未修改的
`6e1910f8` 上重复八轮首次 H.264/H.265 切换，实际解码 MIME 与请求相符，输入通知后
没有再重连；随后用受控事件次序独立复现并修复上述确定缺陷。

## HDMI 恢复

接收端与浏览器实际通过的恢复矩阵：

| 操作 | 编码 | 次数 | 结果 |
|---|---|---|---|
| Mac 显示休眠与唤醒 | H.265 | 3 | 接收器真实失锁，自动恢复 HDR 4K60、音频、同一 SSRC |
| Mac 显示休眠与唤醒 | H.264 | 3 | 同上 |
| 用户拔 HDMI，等待后插回 | H.265 | 1 | 输入 5V 与锁定均消失，插回后同一网页、同一 SSRC 恢复 |
| Mac 整机睡眠与唤醒 | — | 0 | 用户暂不方便操作，独立板端观察器已取消；未验收 |

显示休眠没有改变 EDID/HPD 或重启接收服务。每轮恢复后的 JPEG 为原生 3840×2160，
三处 magic/checksum 帧号一致；HDR 灰阶相对 LUT 模型最大差 3 个 RGB 码。
H.265 显示唤醒后 59.943–59.969fps；H.264 为 59.972–60.174fps。
真实拔插后 59.969fps，HDMI 音调经 Opus 解码峰值 0.106；退出浏览器后 DMA-buf 归零。

上述恢复测试使用候选 `fb3d9bcd`；随后增加的恢复标志消费修复由独立事件顺序测试覆盖。
板端观察器与本地浏览器分开，以便将来进行整机睡眠时仍能保留失锁证据。

## 持续推流工具

[one-kvm-stability-check.mjs](../../tools/one-kvm-stability-check.mjs) 配合
[latency-source.swift](../../tools/latency-source.swift) 的 `--sync-audio=HDMI设备名`：

- 运动、三处帧号及两秒一次的闪块/440Hz 音调来自物理 HDMI，源端音画共用主机时钟。
- 15 秒预热后，每 10 秒记录实际 H.264/H.265 MIME、3840×2160、解码/呈现帧率、
  丢帧/丢包/冻结、内容推进、CPU、RSS、fd、CMA、温度和风扇。
- 三处标记必须先冻结同一解码帧再采样。初版从 live video 分别读 96 次，跨越多帧，
  产生了假“撕裂”；该轮保留为测量工具失败，未用于驱动结论。
- 闪块使用视频合成时间；音调使用 AudioContext 输出时钟，另记录像素回读和音频
  观察间隔的开销。这是软件端点的音画偏差，不是面板/扬声器的光学声学标定。
- 音频只选显式指定的 HDMI 设备，不改 Mac 默认输出。测试进程退出释放自己的
  防休眠断言，显示器消失时隐藏测试窗口，避免覆盖用户的主桌面。

先启动带同步音频的源，再在同一工作区运行（统一登录仍由环境变量传入）：

```sh
VIM4_HDMI_DISPLAY=VIM4-UHD-60 ./motion-source 720 --motion --verify-coherence \
  --hdr-chart --no-labels --sync-audio=VIM4-UHD-60
node tools/one-kvm-stability-check.mjs --exclusive --mode=h265 --seconds=600
```

源程序按既有 Swift 构建方式编译；源端 HDR 偏好由外层测试准备和恢复，浏览器工具
不修改 EDID 或 HDR 参数。JSONL 保存原始测量，不把短时预检查计作 30 分钟耐久。

本轮按用户的时间要求，持续验证缩为 H.265 10 分钟、H.264 5 分钟。它用于检查
修复后的连接、内容更新、资源和音画偏差；30 分钟以上的耐久、隔夜温控与慢性内存
增长仍留到发布前，不据此次短测作长期稳定性保证。

## 本轮持续验证结果

最终 `edc426a1`，Chrome 156.0.8078.47，Mac 经 en0 有线局域网、UDP host candidate
连接板子。输入准备为 4K60 HDR10，白点/峰值 203/1000，编码预算 30000 kbps，
GOP/逐行刷新沿用已验证配置。负载是运动网格、灰阶、三带帧号及音画脉冲，
不是高熵游戏或 30Mbps 实际线速压力；测试期间未并发构建、部署或其他硬件测试。

| 指标 | H.265 | H.264 |
|---|---|---|
| 实测时长 | 604.5 秒 | 302.2 秒 |
| 每约 10 秒窗口数 | 56 | 28 |
| 解码 fps 范围 | 59.923–60.069 | 59.913–60.057 |
| 呈现 fps 范围 | 59.864–60.186 | 59.944–60.057 |
| 实际接收 Mbps 中位 | 1.479 | 5.443 |
| 应用 CPU 中位，单核 100% | 10.64% | 13.77% |
| 整机各核合计忙碌率中位 | 3.65% | 4.04% |
| 温度范围 | 51.1–54.8°C | 50.6–53.9°C |
| 风扇输出范围 | 17–24% | 16–22% |
| RSS 开始→结束 | 77636→83396 KiB | 87748→92100 KiB |
| 后半段 RSS 范围 | 82756–83396 KiB | 91716–92100 KiB |
| CMA 空闲，运行中始终不变 | 264992 KiB | 252476 KiB |

两轮实际 MIME 分别为 H265/H264，尺寸 3840×2160，同一 SSRC，无服务重启，
丢包/解码丢帧/冻结增量均 0；84 个抽样窗口的三带标记一致、内容推进且未被界面遮罩覆盖。
RSS 预热后增幅明显收敛，但短测不能证明没有慢性泄漏。每轮退出后 DMA-buf 严格归零。
逐窗口呈现 P99 最大为 33.6/33.0ms，最大间隔 39.0/48.8ms；像素回读平均约
3.4–7.2ms，音频观察间隔最大 31.7/25.7ms，不能把带探针的结果冒充无探针对照。

302/151 对闪块与音调的软件端点样本，音频晚于视频的中位为 68.4/41.2ms，
范围 40.9–80.5/30.2–48.2ms。首尾各一分钟中位增加 16.4/7.9ms，**不是零漂移验收**；
两种格式都约 1.6ms/分钟，仍需校准独立 AudioContext 输出时钟及观测链，再做更长验证。
未把它归因于内核或宣称已达到光学声学同步精度。

每 10 秒冻结帧的源端绘制到采样年龄中位为 75.6/75.0ms，样本仅 56/28 个，
不是逐帧软件端到端或 P99 目标验收，也不是光子到光子延迟。
