# 2026-10-18：One-KVM H.264 每秒停顿

## 结论与复现

H.264 的一秒 GOP 周期性产生大 IDR，编码、逐包发送和接收解码在关键帧附近集中，
浏览器表现为短暂停顿后追帧。平均 60fps、零丢包和零 freeze 均不能排除该问题。
H.265 已使用逐行刷新，没有复现相同的一秒周期；它的普通帧硬件编码反而略慢。
这是已证实的一项卡顿来源，不是所有观感问题的完整归因。用户在部署后先反馈改善，
随后仍反馈卡顿，并指出观看屏幕为 144Hz；后续仍需区分实际客户端的网络、解码与显示节奏。

基线包为 `vim4-onekvm` / `vim4-amlvenc` 的
`2.5.1+vim4.20261017.28.dev.25.g59190cc`，内核 `5.15.137-vim4kvm`。
One-KVM 源码基线 `9bd71c1a`，编码插件 `a61a4972`。Chrome
`155.0.8059.80`，headless，单观看者，3840×2160/60Hz，Custom 30000kbps，
物理 RTK HDMI 屏持续显示 `latency-source.swift --motion` 网格。
保留 WebRTC 音频轨，但此轮 HDMI 音频为静音，未验收声音质量。
板端原始套接字确认视频发往 Mac 有线地址 `192.168.50.239`。
板温约 55–56°C，CPU0 2208MHz，未改变编码器时钟、QP、尺寸或帧率。

每轮预热 15 秒，测量 120 秒。呈现间隔采用 requestVideoFrameCallback 的
`presentationTime`，无像素回读；它是浏览器提交节奏，不能当作光学显示测量。
同时保留 `presentedFrames` 跳号，避免将回调漏采当作视频丢帧。

| 配置 / 顺序 | 解码 fps | 实收 Mbps | 间隔 P99 / max ms | >50ms 次数 | 新关键帧 |
|---|---:|---:|---:|---:|---:|
| 原版 H.264 A | 59.993 | 30.068 | 54.9 / 63.0 | 115 | 120 |
| 原版 H.265 | 59.972 | 30.054 | 33.6 / 66.6 | 1 | 0 |
| H.264 GOP0、刷新3行 B | 60.001 | 30.050 | 35.1 / 49.1 | 0 | 0 |
| 恢复原版 H.264 A | 59.980 | 30.115 | 53.3 / 81.8 | 139 | 120 |

上述四轮 packetsLost、framesDropped、freezeCount、PLI、NACK 增量均为零。
首轮 H.264 的缓冲驻留均值 2.58ms，H.265 为 2.65ms，候选为 2.71ms，
因此候选的改善不是增加播放缓冲。首轮/候选回调漏采分别 617/264，
累计呈现仍约 60fps；不能据此声称原版每秒丢了五个视频帧。
H.265 的一次 66.6ms 间隔保留在结果中，未将它归因于周期 IDR。

W3C 的 [freezeCount 定义](https://www.w3.org/TR/webrtc-stats/#dom-rtcinboundrtpstreamstats-freezecount)
阈值为 `max(3×近期平均帧长, 近期平均帧长+150ms)`，所以几十毫秒的短顿可能不计入 freeze。

## 定位证据

1. [码率预设](../../One-KVM/src/config/schema/common.rs) 的 Custom 使用 `gop_size=fps`；
   原 [VIM4 管线](../../One-KVM/src/video/pipeline/shared/vim4.rs) 仅为 H.265 开启
   `gop=0 intra-refresh-rows=1`，H.264 因而每秒一个 IDR。
2. 暂停应用，保持相同 HDMI 运动负载，分别独占编码器采集 1200 帧。
   amlvenc sink→src 的 H.264 普通帧中位数约 11.9ms，周期大帧约 16.3ms、
   大小中位数约 618KB；H.265 普通帧中位数约 13.2ms、P99 14.2ms。
   这是编码分段测量，不与其他帧的发送、解码均值相加冒充端到端延迟。
3. 原版复测以内核时间戳抓取 eth0 发送包，按 SSRC/RTP timestamp/marker 聚合。
   大于 400KB 的视频帧中位数约 560KB，首包→末包发送中位数 19.46ms、
   P99 26.37ms、最大 28.75ms，周期中位数约 1000ms。
   正常 60fps 的帧预算只有约 16.7ms。
4. 单独将 GOP 改成 120，接收 encoded-frame 探针记录 60 秒内 30 个关键帧，
   关键帧周期中位数 1999ms。可直接看到大帧前约 49ms 的接收空档，随后数帧
   集中到达。此探针使缓冲均值升至约 11ms，所以不把它与无探针的呈现表直接比较。
5. 不改已安装二进制，通过临时 LD_PRELOAD 仅替换管线中的 GOP/刷新参数。
   B 组消除一秒周期，移除覆盖恢复 A 组后再次出现，构成因果对照。

首轮抓包工具自身有内核缓冲丢包，不能将其帧大小当作完整码流统计。
后续提高独立抓包套接字缓冲并采用内核时间戳，原版复测与候选抓包均零捕获丢包。
H.265 首轮结束恢复模式时，另一个诊断登录替换了会话，得到 HTTP 401；采样已完成，
视频解码持续正常，但该轮清理失败单独记录，后续重新认证恢复配置。

部署后的首轮未固定候选地址，出现另一种不规则尾部：120 秒内 25 次 >50ms，
最大 124.3ms，仍无周期 IDR。Chrome selected pair 指向 IPv4，且该 pair 的
接收字节为零；板端零捕获丢包的短测确认媒体实际发往 Mac en1（Wi-Fi）的
IPv6 地址。这与原始有线 A/B 条件不同，不能据此否定或量化刷新策略收益。
保留该轮 `h264-fixed.jsonl` 与 `h264-fixed-route.jsonl`，后续固定两端有线
候选并重新抓包。多网卡 ICE 路径选择仍需独立排查，不将其笼统归为 H.264
解码问题，也没有为了这次测试关闭系统 IPv6 或 Wi-Fi。

## 修复范围与验证边界

VIM4 H.264 改为 `gop=0 intra-refresh-rows=3`，每帧刷新三行 16px MB；
H.265 保持每帧一行 CTU。保留启动、新订阅和 PLI/FIR 的完整关键帧请求。
只延长 GOP 会降低停顿频率，仍会产生大帧；降低分辨率、码率或提高 I 帧 QP
则改变画质条件，本次不采用。进一步优化 SRTP/RTP 发送可能降低主动恢复时的大帧
尾延迟，但本次没有分别证明加密、系统调用各占多少时间。

修复提交：One-KVM `f007535d`。已构建并部署开发包
`2.5.1+vim4.20261017.28.dev.26.g9bd71c1.dirty`；包在提交前构建，保留原始源码摘要。
独立 One-KVM 正式 tag 比板上组合发布旧，已将同一验证过的二进制重新编号到
组合发布 `.28` 之后；`sources.json` 记录原构建版本与重封装原因。
没有改变其他已安装组件或发布远端版本。

644 项 VIM4 Rust 单测、ARM64 release、网页构建、18 项部署 Python 测试通过。
包校验覆盖 ARM64 ELF/动态库、sudoers、配置保留、实际升级与认证更新 API。
临时 LD_PRELOAD 覆盖已移除，部署后运行的是包内二进制。

两种编码分别通过首个观看者、第二个观看者加入、页面刷新和定向丢包恢复。
丢包测试在 eth0 clsact 上仅匹配当前测试会话的 UDP 四元组，持续 1.5 秒，
H.264/H.265 分别实际丢弃 5328/3649 个包；恢复后均观测到 PLI 增量 1、
新解码关键帧增量 1。移除丢包后，检测到新关键帧及超过 30 个新增解码帧的
耗时分别约 419/315ms；这是恢复检测耗时，不是光学首帧时间。测试过滤器和
本次创建的 clsact 均已删除，原 mq/fq_codel 保留。

部署后固定有线的 H.264 120 秒复测：59.976fps、30.080Mbps，呈现间隔
P99 41.1ms、最大 91.5ms，22 次 >50ms，零新增周期关键帧/丢包/丢帧/freeze。
抓包确认全程目的地址为有线 IPv4，零捕获丢包。周期尖峰已去除，但这轮尾部
比临时 B 组差，仍有零星长间隔（其中 21 次伴随回调跳号）；不能宣称完全无顿挫，
也不选择性地只报告临时 B 组的零次结果。

部署后 H.265 的有线 120 秒测量期间发生客户端会话/编码切换，统计跨越不同接收流，
该轮不能作为完整性能验收，也不能将切换空档计作编码卡顿。原始记录保留为
`h265-fixed-wired.jsonl`，不与上述稳定窗口混合计算。

本次自动化浏览器为 headless，未测量用户的物理 144Hz 屏幕。固定 144Hz 显示
60fps 视频时，一帧通常占 2 或 3 个刷新周期（约 13.89/20.83ms），会有显示节奏
不均；固定 120Hz 则可每帧占两个周期。用户按 120Hz/60Hz 对照建议测试后反馈基本
没变化，因此刷新率不匹配暂不作为剩余卡顿主因。用户端为 macOS 26、M3 Pro、
最新版 Chrome；尚未取得该会话的解码器、接收缓冲和呈现统计，不能将 rvfc 回调
长间隔直接视为光学停顿。
用户另反馈有线连接下 UU 客户端明显更顺。不同客户端的 codec、播放缓冲和解码器
尚未配对控制，因此这是浏览器侧继续调查的线索，不足以判定具体解码器故障。
当前用户会话被动抓包目的地址为另一台客户端，IPv4/IPv6 邻居映射为同一 MAC，
不能套用前述测试机的 Wi-Fi 问题；采样中的三个视频 SSRC 各自首包间隔最大约
29.1/27.1/35.1ms，零捕获丢包，窗口内含用户重连，不跨 SSRC 计算停顿。

最初用 OUTPUT 防火墙丢包会向发送应用返回 EPERM，实际只验证了发送错误恢复，
不能证明网络丢包触发 PLI。该轮的「未见 PLI」断言失败日志保留；改为 tc 静默
丢包后两种编码均通过，没有把失败轮次静默算成成功。

这次是周期卡顿修复，不代表完整低延迟协议达标。尚未完成 30 分钟同连接耐久、
量化画质、光学延迟、Safari、UU 客户端或所有输出分辨率的矩阵验收。
长 GOP 录制的长时跳转/拖动体验也未验收，不能把浏览器流畅度结果代替录屏验收。
原始逐帧/逐次统计、抓包聚合、临时覆盖源码、版本哈希、构建与回归日志位于
`logs/onekvm-h264-cadence/`；该目录按仓库约定不入库。

公共 `tools/one-kvm-smoke.mjs` 新增 `--seconds=120 --warmup=15` 与呈现间隔尾部统计，
