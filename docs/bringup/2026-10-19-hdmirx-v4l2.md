# 2026-10-19：7.3 HDMI V4L2 连续取帧

结论：实验 VDIN 已提供 V4L2 MMAP 连续取帧。1920×1080 RGB24 输入，三轮各
300 帧的运动标记校验通过，稳定段约 10fps。此为私有 DMA 停稳后复制到 vb2 队列的
第一版，未实现持续 DMA、零拷贝或 60fps 采集；默认启动仍为 5.15。

## 实现范围

内核提交 `6ec31e7511a999cbffb17234b9253d2e257ec1e9`，tree
`c05a927125111661fb809cb58875e23dbd3a33fb`。在 [完整快照](2026-10-19-hdmirx-frames.md) 基础上修改
`drivers/media/platform/amlogic/t7-hdmirx/t7-vdin-test.c`，专用测试 DTB 及独占 VPU
窗口的前提保持不变。接收器仍只接受固定 RGB8、逐行 1080p60；没有生产共享 VPU 架构。

- 注册 `t7-vdin-test` 视频节点，编号动态分配；本板测试为 `/dev/video0`。
  支持 QUERYCAP、格式与输入查询、REQBUFS/QUERYBUF/QBUF/DQBUF、poll、MMAP 和 STREAMON/OFF。
  格式固定 RGB24，stride 5760，单帧 6,220,800 字节，仅支持 MMAP。
- vb2 至少排队两个缓冲后启动工作线程。本轮使用四个缓冲。队列耗尽时不再启动取帧，
  新缓冲入队后恢复。已经交给应用、尚未重新入队的缓冲保持不变。
- 硬件始终只访问驱动私有的 coherent DMA 缓冲。每次取帧沿用先丢一帧、第二次写完成
  中断停请求、检查 DMA 完成、再检查 RX 时序的流程；确认成功后才复制至 vb2 缓冲。
  vb2 缓冲不直接给硬件，即使 DMA 停止失败并保留私有内存，也不会写入已释放的应用缓冲。
- `sequence` 每次开流从 0 起；时间戳取第二次写完成中断的 monotonic 时刻，标记 EOF。
  它不是 HDMI 像素输入时间或端到端延迟。应用可见序号不表示所有输入帧均被采集。
- STREAMOFF 等待有界取帧和复制结束，再归还剩余缓冲。最后一个 fd／MMAP 引用释放也会
  停流。视频节点注销先停止队列；视频 fd 引用保护承载队列的对象直到关闭。
- 取帧失败会将队列置为错误并归还缓冲，应用必须关流后重新开流。DMA 停止超时仍按
  既有规则保留私有缓冲、时钟及模块引用至重启；未新增自动重锁、热插拔恢复。
- 流运行时 debugfs `frame` 返回 EBUSY；第二个文件不能抢占已分配的 vb2 队列。
  开关流及 VDIN 重载均不写 RX EDID／HPD。

约 10fps 的限制来自逐帧停 DMA、输入前后检查和 CPU 复制。这一步先验证标准队列和
缓冲生命周期；接下来仍需在明确帧边界、停写及缓冲持有语义后实现持续 DMA 多缓冲。

## 实机证据

独立版本 `7.3.0-rc7-vim4kvm-v4l2+`，完整 Image/dtbs/modules 构建；最终修正后完整
make 再次通过，Image 逐字节未变。2332 个板上模块与最终暂存逐个 SHA-256 相符。
构建目录为 VM `~/build/kernel-edge-v4l2-test`，完整暂存为 `kernel-edge-v4l2-stage`。

运动源为 `latency-source.swift --motion --verify-coherence`，Mac HDMI 输出实际为
1080p60。源图中的 `VIM4 4K60` 是工具原有固定文字，不代表本次支持 4K。
校验位置为 y=85、540、995 的黑白帧号，检查 magic、checksum、三通道一致、三处同号及
跨帧推进；不等同于逐像素保真或光学延迟测量。

| 轮次 | 已校验帧数 | 首末源帧号 | 稳定段帧间隔中位数 | STREAMOFF |
|---|---:|---|---:|---:|
| 0 | 300 | 705 → 2517 | 100.003ms | 94.687ms |
| 1 | 300 | 2530 → 4340 | 100.003ms | 89.735ms |
| 2 | 300 | 4353 → 6164 | 100.003ms | 94.702ms |

每轮开始将四个缓冲全部出队并持有，空队列 poll 200ms 超时；完整缓冲指纹不变。
重新入队后继续取帧。上述稳定段统计排除这次有意暂停，间隔范围 99.999–100.006ms。
首轮早期曾同时进行已安装模块哈希检查；后两轮无此重叠，结果相同，未据此声称完整性能验收。

补充通过三轮各 32 帧的第二文件队列排他、debugfs 排他及反复开关流检查；程序随后不发
STREAMOFF，直接关闭 fd 并解除全部映射，也正常停止。另一次 120 帧检查中确认采集文件
仍打开时 `rmmod t7_vdin_test` 返回 in use，文件及映射关闭后可正常卸载。

最终三轮 VDIN 加载／8 帧取流／卸载后，五项时钟的 prepare/enable 引用均恢复为 0，
视频节点与 debugfs 消失；RX 的 HPD、EDID 哈希、PLL、对齐及尺寸状态未改变。
内核 tainted=0，无新增 WARN/Oops。再做一次原有 debugfs 快照，离线校验通过。

## 失败与修正

首版将 `queue.max_num_buffers` 设为 8，但此内核要求至少 `VB2_MAX_FRAME`，探测触发
WARN 并拒绝注册。删除该设置，使用 vb2 默认上限后重启，最终测试从 taint=0 开始。
早期卸载检查一度在采集程序打开前、另一次在程序结束后执行；不能证明引用保护。
最终编排在同一个执行流程内等待程序显式开流信号，立即检查卸载，得到 in use。
相关失败日志保留；不将编排失败计为驱动通过或故障。

最初模块归档包含额外父目录条目，安装器在写入前拒绝；重打仅含目标 release 的归档后
安装。未放宽路径或符号链接校验。Mac Clang 对原有 DDC/core 测试中的未使用静态表报错，
最终五组实际 C 测试在原构建 VM 的 GCC 环境全部通过，未修改原有测试来屏蔽该警告。

## 复现与验证边界

仅在独占实验启动项及同次构建完整模块集下操作，加载参数沿用快照记录。
先确认 Mac 测试源已覆盖目标 HDMI 屏幕，再在板端编译运行：

```sh
gcc -O2 -Wall -Wextra -Werror tools/hdmirx-stream-check.c -o /var/tmp/hdmirx-stream-check
mkdir /var/tmp/hdmirx-stream-result
sudo /var/tmp/hdmirx-stream-check /dev/video0 300 3 /var/tmp/hdmirx-stream-result
```

[检查器](../../tools/hdmirx-stream-check.c) 只保存每轮首末帧并逐帧输出 JSON；目录必须预先
存在且首末 raw 文件不能已经存在。它会占用采集设备，不能与生产服务或其他测试并行。
`test_stream.py` 编译实际 C 队列／工作线程函数，用 pthread 条件变量协调采集中关流、
缓冲耗尽／恢复、持有缓冲不变、取帧错误及无信号／故障状态拒绝开流；不依赖定时 sleep。
原有 DDC、PHY、core、VDIN 实际 C 回归也通过，strict checkpatch 无错误／警告。
主仓库完整离线测试运行 89 项，无失败，4 项按环境条件跳过。

4K、60fps 持续 DMA、DMA-buf、编码器、输入音频、任意输入热插拔和模式改变、HDCP、
FRL、休眠及完整 `v4l2-compliance` 尚未完成。本轮没有物理拔插 HDMI，错误路径的
线程协调依赖离线测试，不能宣称已验证真实失锁恢复。
