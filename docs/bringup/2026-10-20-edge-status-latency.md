# 2026-10-20：7.x 输入状态等待与端到端延迟

VDIN 的实时输入状态查询误用了带 20ms 等待的启动资格检查。改为即时读取后，
100 次板测的查询中位耗时由 21.037ms 降到 0.012ms；固定 4K60 运动场景中的
周期交付间隙明显减少。端到端中位延迟尚未证明降低，不宣称已经达到全部性能目标。

## 原因、修复和部署

One-KVM 的视频线程每 250ms 调用 `signal()`，经 V4L2 `ENUMINPUT` 进入
`t7_vdin_enum_input()`。原回调调用 `t7_hdmirx_check_video()`，两次读取之间
`usleep_range(20000, 21000)`；该 ioctl 又与采集缓冲操作共用 `video_lock`。
因此查询既阻塞应用取帧，也阻塞 GStreamer 的缓冲操作，仅把查询移到另一线程不够。

Linux `281dd85e6dfe5` 将该回调改为已有的 `t7_hdmirx_check_video_now()`，
每次明确写入当前 status，恢复时清除旧的 NO_SYNC。STREAMON 和快照的双次稳定性
检查保留。`1317fcb8746f30f376420dc193d9a15ac4c83fb7` 补齐 Clang 测试夹具兼容。
实际 C 回归覆盖连续 100 次无等待查询、失锁与恢复，以及启动检查中途信号变化；
同一回归在旧回调上失败。Linux 的 DMA、关闭、profile、刷新六项离线检查通过，
Mac 的 core 回归也通过；profile/刷新回归需要 Linux V4L2 UAPI 头。
默认本地 buffer benchmark 也通过。另在构建容器离线测试同一 `videorate drop-only`
阶段：60fps 的首帧无需等待下一帧即输出，不能将它假定为额外一帧延迟后直接删除。

保留 Image `375bfd9`、音频 DTB、Wave5 `4f00b3c`、One-KVM `414e88b9`，
只覆盖 VDIN 模块；版本和摘要见 [源码锁](../../packaging/kernel-edge/sources.toml)。
新归档 SHA256：`f2c5ac54f2edd18188ff9a0d549b648dccb166fe955e9d914412943d629c835c`。
公共内核头文件及配置与保留 Image 一致，仅改 VDIN 私有回调；未使用 force，
模块为 intree、taint=0。单模块不附带另一 vmlinux 的 split BTF，处理边界同
[Wave5 覆盖记录](2026-10-20-edge-cyclic-refresh.md)。没有部署新整包 Image。

```sh
make O=/home/deepdream/build/kernel-edge-uhd1-test CONFIG_DEBUG_INFO_BTF_MODULES= -j8 \
  drivers/media/platform/amlogic/t7-hdmirx/t7-hdmirx.ko \
  drivers/media/platform/amlogic/t7-hdmirx/t7-vdin-test.ko
```

一起指定两个目标，使 modpost 看到接收器导出的符号；仅打包 VDIN，不安装此次构建的
接收器模块。确认 VDIN ELF 无 `.BTF` 后 strip/XZ。安装先备份旧模块和清单，停止实验
应用并确认引用和 DMA-buf 归零；只 `rmmod t7_vdin_test`，不使用会移除接收器依赖的
`modprobe -r`。原接收器保持加载，重载 VDIN 时恢复 `nv12=1 direct_dma=1`。
应用和网关恢复后保留原 H.265 模式。Image、接收器、Wave5、生产应用、助手和默认
5.15 启动项均有摘要保护。旧模块在板上私有备份的 `vdin-status/` 中。

## 软件端到端短测

同一 Mac 的物理 `VIM4-UHD-60` 显示器，原生 3840×2160 栅格、60Hz、运动网格；
One-KVM 请求 30000kbps，无缩放，音频开启、信源静音，单观看者。
Chrome headless；期间从 155.0.8059.85 自动更新到 156.0.8078.47，各轮见下表。
跨版本的 H.265 结果仅作历史参考，后续对照固定本地 156 快照及其实际运行版本。
板端按浏览器视频 SSRC 确认实际媒体经 eth0 发往
Mac 有线 `192.168.50.239`，相关抓包零捕获丢包。

源端绘制帧号到浏览器 compositor 提交为软件端到端终点，不是光学显示延迟。
GPU 优先裁剪的像素读回中位约 2.3–2.8ms，旧 CPU 画布约 23.3ms；这是测量开销
改善，不能冒充视频传输减少了 21ms。源端和浏览器共用 Mac 时钟。

|---|---:|---|---|---:|---|---|---:|
| 原状态查询 | 150 | H.265 | 155 | 1296 | 64.4/81.4/84.2 | 47.8/64.2 | 14 |
| 即时状态查询 | 120 | H.265 | 156 | 1140 | 68.1/74.4/80.2 | 33.8/40.0 | 0 |

| 即时状态查询 | 120 | H.264 | 156 | 1173 | 68.6/83.4/88.2 | 37.9/47.9 | 0 |

各轮约 60fps，零新增 packetsLost、framesDropped、freeze 和周期完整关键帧。
新轮 H.265/H.264 的实际视频缓冲均值分别为 2.43/3.22ms，与原 2.47/3.19ms 接近；
没有增加缓冲来隐藏停顿。呈现回调漏采分别为 362/157，不当作视频丢帧。
H.265 板端帧首包间隔 P99 从约 36ms 降到约 20ms，超过 25ms 的间隔由约
每秒 3.7 次降到 0。帧首包/末包时间是内核出站抓包端点，不是物理网线时间。

这些是定位短测，窗口长度和时钟校准版本有所不同，并非三组匹配配对验收。
保留 API 等待和交付间隔的直接证据，不据此宣称端到端中位数下降、全部目标达标
或已经与 5.15 全场景等效。源端扫描、编码、网络、解码及呈现仍共同构成延迟。

随后使用 `VIM4_TEST_CHROME` 固定同一份 156.0.8078.47 浏览器，保留相同运动源、
4K60、30Mbps 请求与音频设置，不读取像素，各预热 15 秒后采样 120 秒。
反向装回旧模块，再恢复新模块，应用仍为同一 `414e88b9` 二进制。

两轮均无新增丢帧、丢包、freeze、PLI、周期关键帧，零抓包丢失；实际媒体均走 eth0。
板端帧首包间隔 P99 分别为 36.16/19.71ms。这组控制排除了浏览器自动升级和读回
开销，但仍只有一组固定版本配对；不把它写成三组配对或完整客户端矩阵通过。

## 测量失效与未采用的方案

首次新驱动 H.265 轮次有 28 个样本的旧固定时钟映射超出 2ms，最大 2.2ms，
端到端整轮判为无效，原日志保留；该轮约 60fps、零丢帧/丢包和抓包间隔仍可用于
各自的观测，不能作为有效端到端成绩。没有放宽旧阈值或事后删除慢样本。
新工具显式逐样本校准当前 wall clock，记录校准不确定度并拒绝超过 2ms 或突变；
两轮有效短测的不确定度最大 1.05ms、零无效帧号。旧日志仍使用原校验规则。
长测的周期统计和按时间窗口匹配帧号见 [测量方法](../latency.md)。

曾独立尝试用采集 PTS 替换编码完成时间生成 RTP 时间戳。两种格式的 RTP 间隔
变为 16–17ms，但实际交付仍有约 35ms 尾部，端到端没有明确改善；该应用候选已
回退，One-KVM 源码保持 `414e88b9`。721 项 Rust 测试及 release 构建通过只证明
候选可构建，不能代替性能收益。本地候选 ELF、补丁及对照日志留在忽略的 build/logs，
没有把未验证收益的开关加入生产代码。

原始记录位于 `logs/kernel-edge/edge-{latency-gpu,status-calibrated,input-query}*`；
查询前后、原回调失败回归、模块构建日志及 SHA 均保留。
同连接 30 分钟耐久尚需完成，当前不以短测代替长期验收。
