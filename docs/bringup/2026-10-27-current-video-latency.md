# 2026-10-27：当前 One-KVM 延迟与 SDR 缩放瓶颈复测

当前 5.15、One-KVM、4K60 SDR、有线局域网、40Mbps 配置下，H.265 软件端到端
中位数约67ms，WindowServer报告显示到接收浏览器提交合成约35ms。
原尺寸交帧到编码入口只有0.2ms；编码约13.4ms，发送大帧的尾部仍值得优化。
4K降1080p额外经过约14ms的GE2D缩放，抵消较小尺寸的编码收益。
本轮完成实测和缩放候选A/B/A，未保留生产代码或配置改动。

这里的软件端到端是**源端开始绘制同一帧→浏览器presentationTime**，后者是提交合成器，

WindowServer的displayTime是系统报告的显示端点，不能当作物理HDMI首/末像素到达。
draw→display包括源程序绘制和显示调度，因此约32ms不全属于KVM内部。

## 同帧关联与观察开销

每个主窗口预热15秒及像素采样预热3秒，随后测120秒。临时LD_PRELOAD记录V4L2时间戳、
GST各pad、编码API、appsink、SRTP发送；完整AU写入/dev/shm，测后离线解码三带帧号。
SRTP使用完整包长序列与唯一因果窗口匹配AU，再独立核对AU像素和浏览器rtpTimestamp。
H.265/H.264/缩小H.265分别解码8443/8375/8439个AU，三带均有效。
浏览器同帧配对数1082/947/1136；H.264的6个、缩小H.265的3个回读与RTP帧不符样本保留
在rejected文件并剔出同帧分段，没有删慢帧。H.264不足1000样本，不作P99验收。

板端MONOTONIC连续映射Mac时钟，三窗口跨机误差界最大1.84ms；板内分段使用同一时钟。
原尺寸H.265探针写AU开销中位0.127ms、P99 0.439ms，不能宣称观察无开销。
卸载探针后的H.265重复窗口为67.04ms，与探针窗口66.87ms接近，但单轮不能证明零扰动。
源端显示探针通过已授权的签名应用启动；H.264前56个配对帧早于它启动，显示分段仅891帧。

## 当前软件端到端

除最后一行外均有板端探针；全表持续解码、presentedFrames增量均约60fps。
“实际Mbps”来自接收统计；配置40Mbps不代表低复杂度1080p也产生40Mbps。

| 输入→输出 / 编码 | 实际Mbps | 同帧数 | P50 ms | P95 ms | P99 ms | max ms |
|---|---:|---:|---:|---:|---:|---:|
| 4K→4K H.265 | 39.14 | 1082 | 66.87 | 74.47 | 77.93 | 82.57 |
| 4K→4K H.264 | 40.07 | 947 | 66.62 | 80.88 | 样本不足 | 90.48 |
| 4K→1080p H.265 | 22.77 | 1136 | 70.07 | 73.10 | 75.64 | 86.45 |
| 恢复生产H.265，无板端探针 | 39.07 | 1039像素配对 | 67.04 | 73.75 | 76.69 | 79.65 |

恢复窗口draw→display中位32.38ms、display→compositor中位34.62ms/P95 41.32ms。
这些分位数各自独立统计，不能相加充当同帧端到端。分段窗口中H.264的display→ready为
16.16ms/P95 16.24ms；缩小H.265为16.16ms/P95 16.22ms，另有一帧32.84ms。
前段等待主要发生在驱动交帧之前；这不是发现了可直接删除的一帧缓存，参见
[VDIN1交付时序](2026-10-25-vdin1-frame-handoff.md)。本轮未重新追踪图像写完成中断。

所有主窗口framesDropped、packetsLost、freezeCount增量为0。H.265恢复窗口回调间隔
P95/P99为32.8/34.7ms，无超过50ms间隔；另跑60秒、不做像素回读且关闭显示探针的对照，
约60fps，间隔P95/P99为25.6/31.4ms、最大48.1ms。回调漏采不能直接算呈现丢帧。
H.264有44次回调间隔超过50ms、最大64ms，P95/P99为43.2/49.7ms；没有同条件无回读对照，
尚不能把全部回调尾部判为屏幕停顿，也不能仅凭60fps和零freeze宣布其平滑度通过。

## 交帧之后的耗时

下表为同帧P50/P95，单位ms；“发送”从首包send入口到末包send返回。

| 分段 | 4K H.265 | 4K H.264 | 4K→1080p H.265 |
|---|---:|---:|---:|
| V4L2 ready→编码入口 | 0.195 / 0.328 | 0.182 / 0.326 | 14.143 / 14.405 |
| 编码入口→完整编码输出 | 13.364 / 14.425 | 12.498 / 14.178 | 4.071 / 4.370 |
| 应用取出AU后→首包发送 | 0.716 / 1.932 | 0.711 / 2.991 | 0.536 / 0.902 |
| 同帧首包→末包发送 | 2.530 / 7.444 | 2.208 / 9.710 | 1.694 / 3.068 |
| 浏览器末包接收→提交合成 | 2.300 / 5.600 | 2.800 / 6.900 | 1.300 / 4.500 |
| V4L2 ready→浏览器提交合成 | 19.464 / 26.963 | 18.833 / 33.078 | 21.983 / 25.052 |

编码输出→appsink与appsink→应用取出分别约0.1/0.05ms；表中应用取出端点排除探针写盘时间。
网络跨机差值接近时钟误差界，有少量负估计，不能报告“负网络延迟”或精确亚毫秒值。
解码处理与jitter residence可能重叠，不能再把它们加到receive→compositor之上；定义参见
[WebRTC统计规范](https://www.w3.org/TR/webrtc-stats/)。

发送尾部另使用整个120秒窗口所有视频帧，不依赖浏览器回读抽样，端点为首包→末包send入口：

| 编码 | 帧数 | P50 / P95 / P99 ms | syscall均值 / 包间工作均值 ms |
|---|---:|---:|---:|
| 原尺寸H.265 | 7199 | 2.618 / 8.111 / 9.208 | 1.242 / 1.822 |
| 原尺寸H.264 | 7200 | 2.199 / 11.482 / 12.644 | 1.271 / 1.819 |

## 缩放A/B/A：主要时间在GE2D阻塞调用

同一4K输入、1080p输出，通过临时管线替换对照现有amlvconv与已安装vim4scale，最后恢复。
每项预热18秒后测60秒，各3599个稳态缩放帧；三组全AU共14527帧，三带帧号均有效。
浏览器同帧数600/552/512，解码和呈现约60fps，无丢包、丢帧或freeze。

| P50，ms | amlvconv A1 | vim4scale B | amlvconv A2 |
|---|---:|---:|---:|
| 缩放pad入口→出口 | 14.279 | 13.775 | 14.124 |
| GE2D两次ioctl合计 | 13.693 | 13.655 | 13.478 |
| allocator调用合计 | 0.0065 | 0 | 0.0063 |
| 编码入口→输出 | 4.053 | 4.053 | 4.051 |
| 驱动交帧→浏览器提交 | 21.915 | 21.369 | 21.989 |

缩放前后各约0.05ms，分配也不是主要成本。GE2D阻塞blit（request 0x4702）平均
13.48–13.61ms，配置调用约0.026ms；这里包含内核、硬件完成等待及唤醒调度，未再拆分。
vim4scale仅观察到约0.5–0.6ms的交帧后收益，不满足正式优化门槛，保留原路径。
没有三组120秒A/B/A或30分钟耐久，因此不是候选正式验收。

## 优化顺序与限制

1. **原尺寸路径优先发送批处理。** 在SRTP之后尝试sendmmsg小批次，帧尾立即发送，
   同时覆盖ICE、重传、包序、音频及HID公平性。[此前离线/板端回放](2026-10-25-rtp-send-benchmark.md)
   的batch32只证明可降低系统调用成本，不能承诺当前端到端能省完整9–13ms尾部。
2. **缩小输出优先验证采集侧缩放。** 尝试VDIN直接交付目标尺寸，避免独立GE2D全帧处理；
   需解决宽度向下对齐64、超宽屏比例/行跨度以及原尺寸快照共存，见
   [现有SDR缩放决策](2026-10-27-sdr-scale-controls.md)。本轮未验证该候选，不能保证省14ms。
   本结果只适用于SDR GE2D，不能套用HDR的Mali/P010路径。
3. **编码器fast packing单项对照。** 原尺寸12.5–13.4ms仍值得调查，但只有固定输入、
   同码率/画质、码流和恢复回归通过才保留。[已有审查](../encoder-fast-packing-audit.md)
   的mode1尚未实测；mode2/3不能直接开启，不采用已有失败记录的超频。
4. **当前不优先缩减队列或浏览器缓冲。** 原尺寸ready→编码仅0.2ms；接收后约2–3ms，
   现有证据不支持简单删缓存可省整帧。源端约32ms绘制/显示调度也不能算KVM优化收益。
