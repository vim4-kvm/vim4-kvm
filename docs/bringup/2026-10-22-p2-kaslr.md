## 运行证据与原因

服务、空 LUN 和 UDC；不安装候选，不修改启动项：

```sh

  python3 -u logs/p2-20261022/reboot-check.py

```

|---|---|---|
| 重启前 | `02758442-3e85-4785-840b-c8504e7567bf` | `ffff800080000000` / `ffff800080010000` |
| 第一次后 | `bd6b410d-eda8-40fd-bf4e-36fe3888b3bc` | 同上 |
| 第二次后 | `a1e99c9a-e1ae-483d-ad3b-3af0fd06e664` | 同上 |

三次均有 `KASLR disabled due to lack of seed`；`CONFIG_RANDOMIZE_BASE=y`，
命令行无 nokaslr。实时 `/chosen` 只有 bootargs、bootloader_build、PD 快照和 name。
注意 Linux 会消费并擦除种子，单凭运行后属性缺失不能证明启动前缺失；本结论同时依据
日志、固定地址、下面的固件代码和磁盘 DTB 路径。

U-Boot `0d5a3d7848377c0093ecdfb15de80cf2bf83e928` 的
`arch/arm/lib/bootm.c:449` 只在 DT 已有 kaslr-seed 属性时更新；7.3 DT 没有它。
旧路径把单个 32-bit 硬件 rand 扩成 u64、以本机字节序写入，也没有 rng-seed。
T7 `rand()` 的等待无超时，不能直接拿来作为可靠的可选启动交接。

7.3 `arch/arm64/kernel/pi/kaslr_early.c` 在平台 RNG probe 前使用大端 64-bit
kaslr-seed 或 CPU RNDR；本 CPU 不提供 RNDR，晚期 hwrng 不能补救本次 KASLR。
`drivers/of/fdt.c:1111` 已读取 rng-seed、调用 add_bootloader_randomness 并清除属性，
无需再补一份内核读取实现。当前 `rng_current=fe440788.rng`、`rng_quality=1024`、
`rng_core.default_quality=1024`；这是 hwrng 核心默认质量上限，不是实测熵证书。
本轮不改内核配置或 hwrng 质量，CRNG 三次初始化分别约 0.267295/0.267254/0.263950 秒。

## 离线实现、提交与验证

- VM 工作树 `/home/deepdream/src/u-boot-p2-kaslr`，分支 `vim4-p2-kaslr`。
- 提交 `d1c2033e4b3fed01b6f227b4bcae29833f5e78fc`，基于 pd-handoff `0d5a3d7848`。
- 独立输出 `~/build/u-boot-p2-kaslr`、`u-boot-p2-kaslr-stub`、
  `u-boot-p2-kaslr-candidate`；未修改/切换其他工作树，无推送。

board fixup 在 /chosen 创建后写一个大端 u64 kaslr-seed 和独立 32 字节 rng-seed。
硬件操作严格按厂商 5.15 common_drivers 的 version-2 CFG/OUT0 握手：
`0xfe440788` bit31 启动、等待 bit31 和 bit0 清零、读 `0xfe440790`。
每个等待最多 10 ms；超时、明显恒定输出或 FDT 空间不足时清除旧种子并继续启动，
不打印种子、不保存环境、不用定时器/伪随机回退。两类种子使用不同样本。
这只是候选，没有证明 U-Boot 阶段硬件握手与两种内核启动实机通过。

禁用 VIM4 旧 CONFIG_AML_KASLR_SEED，避免 boot_jump 覆盖新属性。
显式 nokaslr 仍由内核处理；旧 ramdump_enable/ramoops_io_en 隐式禁用策略不再应用，
调试需稳定地址时必须显式传 nokaslr，已在候选文档说明。

`tools/test-vim4-random-seed.py` 编译实际函数及 libfdt，以受控 MMIO 覆盖两状态位超时、
陈旧种子清理、重新尝试、字节序、独立样本和逐容量 FDT 分配失败回滚：

```text
PASS: fresh seeds, FDT encoding, retry, bounded RNG faults and allocation rollback
PASS: unchanged Request, PS_RDY gate, raw PDO retention, hard reset, vendor/mainline FDT, no fixup I/O
```

第二行为既有 PD 回归。git diff --check 通过，bundle verify 通过。
构建使用 GCC 12、私有 O=；Mac `/usr/bin/lockf /tmp/vim4-heavy.lock` 包住全部 make，
采用仓库 VIM4.md 现有兼容告警参数，不掩盖新源码错误。BL33/BL33Z 构建成功；
厂商 LCD/MMC/USB 等原有告警和 EFI RWX 链接告警仍存在，不宣称零警告。

## rngtest 1200 块的解释

复核[此前样本](2026-10-22-edge-diag.md)：100 块 0 失败、100 块 1 次 Long run、
1000 块 1 次 Long run。板端包为 rng-tools-debian 2.4。依据
[rng-tools 的 FIPS 实现](https://github.com/nhorman/rng-tools/blob/master/fips.c)，
每块 20000 bit，Long run 检测至少 26 个相同比特；其他测试是不同统计事件。

保留的 1000 块样本 SHA `15a401cab353e0793f3c74785ef86dc56e08d82be375481c9c19e0dd9f777f8a`，
按 rngtest 跳过初始 4 字节后复核，0-based 第 347 块最长 run=26，其他块最长不超过 24；
没有重新采样来覆盖旧失败。`rng-statistics.json` 保存直方图及模型。

在独立公平比特假设下，以状态 1–25 的连续 run 长度递推，单块出现 ≥26 run 的概率
约 `0.0002976214`；1200 块期望失败 `0.35715`，至少两次的二项上尾概率约 `5.042%`。
因此这是偏少见、约 95% 边缘的可发生事件，**不是确定的硬件故障，也不能轻率称完全正常**。
原 1000 块是看到失败后追加，且有多个统计检验，不能把这项事后上尾概率当预注册的
显著性检验或熵估计。仍缺跨冷启动、温度/电源条件、独立固定规模数据及熵源评估。
