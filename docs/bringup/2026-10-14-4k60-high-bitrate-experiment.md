# 2026-10-14：4K60 高码率编码实验

VIM4、内核 5.15.137-vim4kvm，编码插件基线 7f34fb35。
从该源码复制构建实验插件，仅将 `PROP_BITRATE_MAX` 从 12000 提高到
100000 kbps；在 `/tmp/vim4-high-bitrate` 通过独立 GST_PLUGIN_PATH 和
GST_REGISTRY 加载，没有覆盖已安装插件，也没有修改应用码率配置。

独占停止 One-KVM 后，以 khadas 运行 encoder-budget.py，直接采集
HDMI 3840×2160 SDR NV12，60fps 编码预算、GOP120、默认 QP。
Mac 物理 AML HDMI 显示器运行 `tools/latency-source.swift --motion`：
移动彩色格子、文字和帧编号，不是随机噪声或固定回放的视频素材。
H.264/H.265 依次测试，输出 Annex B 保存到 tmpfs。
20–60 Mbps 每档 1800 帧（约 30 秒），80/100 Mbps 每档 3600 帧（约 60 秒）。

| 目标 Mbps | H.264 平均 / 1 秒峰值 Mbps | H.265 平均 / 1 秒峰值 Mbps |
|---|---|---|
| 20 | 20.85 / 26.12 | 19.29 / 25.66 |
| 30 | 30.87 / 39.42 | 24.28 / 31.66 |
| 40 | 41.30 / 52.58 | 24.82 / 31.53 |
| 60 | 54.09 / 66.71 | 25.45 / 31.62 |
| 80 | 60.31 / 70.81 | 26.31 / 31.83 |
| 100 | 61.34 / 72.02 | 26.28 / 31.55 |

所有档位输出到 appsink 的平均帧率为 60.01–60.02fps，协商码流尺寸均为
3840×2160。12 份完整码流均通过独立 Ubuntu FFmpeg 软件解码
（`-xerror -err_detect explode`），传回本机后的 SHA256 与板上文件一致。
H.264 100 Mbps 档帧到达间隔 p99 22.37ms、最大 26.75ms；
这不是端到端延迟，也没有单独测网络丢包、浏览器呈现或画质收益。
采样温度约 50.8–50.9°C，不是完整热稳定测试。

结论：12 Mbps 是软件限制；本轮证明 H.264 在该运动画面下可以持续约
61 Mbps、接近 60fps。100 Mbps 参数被接受不等于实际持续输出 100 Mbps。
H.265 在这组画面下约 26 Mbps 趋于平缓，不能把它解释为硬件上限。
尚未测到绝对硬件码率边界，也不能把每档 30–60 秒当作长期稳定性验收。
H.265 解析出的码流声明 main tier / level 5；本轮未验证其与高码率、
4K60 的规范一致性及浏览器硬件解码兼容性，不能据此直接发布更高档位。

结束后恢复 One-KVM，保持现有插件 12 Mbps 上限。HDMI 服务 InvocationID
仍为 5adb6d1c9b494584996befd0f64d2877，没有重启或重新协商 HDMI。
已安装的 vim4-amlvenc 与 vim4-onekvm 均通过 dpkg 文件校验。
本机证据在忽略入库的 `logs/encoder-high-bitrate/`：各档测量 JSON（厂商库
另有 stdout 日志，以含 codec 的 JSON 行为准）、码流、构建日志和运动源时间戳。
