## compliance panic 与定位边界

新pstore显示compliance窗口先在t=159.247秒完成同样的power_test；之后t=159.485128秒
再次GET确认VDEC/NIC3均on，CCF报告499999992Hz。随后：

```text
[159.485176] SError Interrupt on CPU0, code 0xbf000002 -- SError
PID: 2040 Comm: v4l2-compliance ... 7.3.0-vim4kvm-vdec4+ #2
pc: _regmap_read+0xd0/0x270  lr: _regmap_read+0x68/0x270
x20=0x2638 x4=0x2638 x3=0x2638
Kernel panic - not syncing: Asynchronous SError Interrupt
_regmap_read -> _regmap_update_bits -> regmap_update_bits_base
  -> dos_enable+0x6c/0x88 -> vdec_enable+0x10c/0x158
  -> aml_vdec_runtime_resume+0x40/0x80 -> pm_generic_runtime_resume
  -> __rpm_callback -> rpm_callback -> rpm_resume -> __pm_runtime_resume
  -> fops_vcodec_open+0x1bc/0x2a8 -> v4l2_open -> chrdev_open -> openat
```

对同次构建模块离线objdump：dos_enable基址0x3330，`+0x68`调用
`regmap_update_bits_base`，传入byte offset `0x2638`、mask `0x80000000`、value0，
返回位置为`+0x6c`。对应 `MDEC_PIC_DC_CTRL` word `0x098e`，物理地址
**`0xfe322638`**，操作为读取后清bit31；此前按代码顺序已走过DOS_GCLK_EN0和GCLK_EN。
完整寄存器/调用栈在新dmesg pstore的517行起，反汇编在 `dos-enable-objdump.txt`。

这比前轮 `regmap_write/GCLK_EN` 附近的栈更具体，但仍是异步SError，不能断言
`0xfe322638` 是唯一致因，也不能证明之前GCLK写完全成功。**SMC报告域on、全局reset
寄存器可读，并不足以证明内部MDEC寄存器可安全访问**。异常发生在open初始化，
没有提交H.264微码加载或解码DMA任务；不属于码流错误、格式或吞吐量失败。
没有跳过该寄存器、试其他格式、重载候选或重复compliance。
