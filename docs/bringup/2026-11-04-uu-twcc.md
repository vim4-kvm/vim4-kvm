# 2026-11-04：UU TWCC 发送端带宽估算

在 [RR/REMB 首版](2026-11-04-uu-adaptive-bitrate.md) 上补齐 TWCC 发送端闭环。
源码为 One-KVM `4fe2bac7`（主体 `daf130d4`，初始化修复 `9666d02d`，覆盖门禁 `ef029696`）；实现与边界见 [twcc.rs](../../One-KVM/src/uu_remote/twcc.rs)
及 [UU 文档](../../One-KVM/VIM4.md#uu-远程)。离线通过不等同官方客户端或弱网验收。

## 实现

协商 v1 transport-wide 扩展后才写入序号。拦截器位于 NACK 下游，
音视频与每次重传共享传输序号；发送失败移除历史，RTCP 从所有媒体入口消费。
FMT=15 的状态块、接收时间增量及发送历史共同形成吞吐、延迟趋势和丢包观测。
序号和参考时钟回绕、重复/重叠反馈、反馈超时、路径切换与应用受限流量均有处理。

控制使用被动延迟/丢包 AIMD，并非 Google GCC 的完整移植。不插入等待队列、
探测包或额外帧延迟；不能据此宣称端到端延迟已测量为零增量。
新鲜 TWCC 优先于 RR，REMB 仍限制预算；无有效 TWCC 回退 RR。
编码器更新沿用 Wave5 在线码率通路，用户手动画质和固定 QP/无损模式不被覆盖。
状态 API 的 `twcc_estimate` 提供估算预算、已确认吞吐、延迟趋势、丢包和样本年龄。

## Mac 实流暴露的反馈覆盖问题

用户随后接入 dev.20。12 个样本中视频 RR 丢包恒为零、发送约 60 fps，
TWCC 却报告 67.1%～83.0% 丢失、确认吞吐约 9.2 kbps，目标被压至 1000 kbps。
这不是带宽估算验收通过；停止观察并恢复 dev.18，纯视频再次验证持续解码、无采集重建。

源码审查确认缺少该媒体 `transport-cc` 反馈协商检查，也没有视频确认覆盖门禁。
`ef029696` 要求扩展与反馈能力同时协商，且只有确认过视频包的 TWCC 才接管视频码率；
仅音频确认时继续使用 RR。增加音视频确认数、`usable_for_video` 和不含凭据的协商日志，
后续实测须区分未协商视频反馈与已协商但未收到视频确认，不能只凭小吞吐判断原因。
新增回放验证仅音频确认不会将视频降至最低码率、未协商反馈时不编号。
覆盖门禁版 `2.5.1+vim4.20261027.3.dev.21.gef02969` 已部署并保留。
Mac H.265 与 Opus 均协商 `transport-cc`、扩展 ID 3，但视频确认始终为零，音频确认持续增加。
约 3 分钟观察中 `usable_for_video=false`，RR 丢包为零，目标保持 4000 kbps、发送约 60 fps，
证明回退保护生效，不能宣称 H.265 视频 TWCC 已验收。为继续离线定位，主动结束观察，未满 10 分钟。

`4d21b7d2` 增加实际 SRTP 双端回归：H.264、H.265 携带 UU 元数据和分片时均收到视频 TWCC。
临时改为 H.264 的官方客户端对照也收到视频确认，`usable_for_video=true`，结束恢复 `auto` 偏好。
对照中一次连接约 39 秒后进入 Disconnected；用户随后表示可能是手动断开，且之后未复现。
不把它登记为已确认的自动断线故障，也不把这次短观察宣称为稳定性验收。

H.264 对照暴露同时间戳包漏算：TWCC 将到达时间量化到 250 微秒，同一批视频分片可共享时间戳。
原统计跳过相同/倒退的时间，低估吞吐。`4fe2bac7` 保留所有已送达字节，乱序包计入当前速率窗口，
但不把倒退时间送入延迟回归；新增批量分片、相同时间戳和负增量回放。部署结果见下一节，实流吞吐复核仍待完成。
