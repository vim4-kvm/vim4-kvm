# 2026-11-04：T7 H.264 分辨率与码流边界

接续 [H.264 基础修复与逐帧验收](2026-11-04-hwdecode-parity.md)。UHD 运动样本
与 4096×2304 均已逐帧逐字节匹配，非平坦量化矩阵仍失败；正式启动继续保留
原内核，完整厂商格式对齐尚未完成。

## 第六轮：UHD 正确，4096 宽度触发重新配置

候选源码 `0959f0fd1ac831910b6523fc91c216ab5b70088d`，build ID
`2ef382d4190b8f05066679a5ac6576983243dbb0`。为 T7 单独登记 H.264 与输出格式
范围，保留 S4 的原有限制；同次 Image、DT、完整模块封包通过。

原四组 Baseline/Main/High/1080p 样本保持原字节与哈希，重新逐帧验证通过。
新增 3840×2160 High、B 帧样本的 16 帧全部匹配。4096×2304 样本返回八帧全零
数据，串口每帧记录固件状态 `0x11`，没有进入正常 slice header/data 完成路径。
GStreamer 正常退出不能证明解码成功；像素门禁拒绝了这个结果。
首次失败后停止，非平坦量化矩阵样本尚未上板运行。

## 4096 宽度字段修复

[厂商 vmh264.c](https://github.com/vim4-kvm/common_drivers/blob/31619c527655514b4c89516ef609b6db1dd47db6/drivers/media_modules/frame_provider/decoder/h264_multi/vmh264.c)
的 `get_dec_dpb_size_active` 明确把八位宏块宽度零解释为 256；高十六位另存
宏块总数。当前驱动写入 256 时没有截断到八位，溢出位进入面积字段。

提交 `e7a9d2215f2256595a8f729b53146d39bae93922` 限定宽度字段。回归通过真实
SPS 参数配置函数生成固件输入，再反解 3840 与 4096 宽度、宏块面积和高度；
旧实现无法通过边界用例。24 项主机回归与 strict checkpatch 通过，第七轮
硬件复验确认此项修复；不代表其他边界也已通过。

## 未验边界

当前范围仍是八位 4:2:0、逐行、单 slice。非平坦量化矩阵样本已从
码流确认 PPS scaling matrix 标志，实测仍不正确。厂商还允许部分竖向尺寸，
不能把当前 4096×2304 矩形范围说成全部方向已对齐。多 slice、隔行、错误恢复、
多实例和长时间共存也不能由短样本推定通过。

## 第七轮：4096 边界通过，非平坦矩阵失败

候选源码 `e7a9d2215f2256595a8f729b53146d39bae93922`，build ID
`b2c04c9a9a7ddd9350869598bc0afa3e158ee9d1`。前六组样本全部逐帧匹配，包含
4096×2304 High 的八帧。该样本从固件重新配置请求变为正常解码，确认宽度
字段修复解决了本次最大尺寸失败。

随后 `high-jvt` 返回 16 个非零帧，正常 header/data 中断，但像素不一致。
该流 PPS 携带非平坦 scaling matrix 标志，V4L2 已给出解析并应用回退规则的
矩阵；驱动仅取得控制指针，未把矩阵写给固件。

原内核身份与文件证明恢复一致，五秒 H.265 接收约 59.76 fps，零新增丢帧、
冻结或丢包，UDC/performance 正常。证据在 `build/hwdecode-parity/run7/` 和
`logs/hwdecode-parity-r7/`。

## 第八轮：参数槽补写无效，已撤回

## 原生参数头候选

候选 `520cbf7cccdebd8b0d28cb83ab018d531c5a998f` 从标准 V4L2 控制重建
SPS/PPS，让固件解析非平坦矩阵。矩阵由 raster 顺序转为码流 zigzag，写入
时插入防止起始码仿真的字节；有界写入覆盖长 POC 循环、符号极值和容量不足。仅非平坦
矩阵使用私有 DMA 输入，分配或序列化失败直接返回错误。重新配置中断不当作
帧完成；私有输入遵守原有停机与永久隔离约束。

28 项主机回归及 strict checkpatch 通过。替换 JVT 样本 SPS/PPS 后软件解码
的全部 16 帧与原码流逐字节一致。以上只证明序列化与主机路径，实板结果另记。

## 第九轮：原生参数头需要第二阶段握手

上述候选 build ID `96154b659b77194b954105a808283b900ca6749e` 完整启动，
MDEC 生命周期与 V4L2 compliance 通过。首个 JVT 样本在首帧前超时，没有
输出数据。固件只发出一次 `0x11` 配置请求，随后停在 `DPB_STATUS_REG=0xf2`、
`AV_SCRATCH_0=1`，没有 slice header/data 中断。其余样本按首错停止规则未运行。

厂商 `vmh264.c` 的 IRQ 先写 `CONFIG_DONE`，随后工作线程在
`DEC_RESULT_CONFIG_PARAM` 分支重新写入 DPB 数量到 `AV_SCRATCH_0`。
候选缺少第二步，固件解析参数头覆盖了原来的缓冲配置。提交
`842774352633005f5e0823d9cecd4d7e9dcdfe60` 补齐这一步，复用初始配置相同的
数量计算；不返回帧、不释放 DMA。29 项主机回归、strict checkpatch 和驱动
编译通过，硬件效果尚未复验，不能宣称矩阵已支持。

本轮正常恢复原内核完整证明，五秒 H.265 接收约 59.76 fps，零新增丢帧、冻结
或丢包。服务、UDC、performance 与 taint 均保持原状态。证据在
`build/hwdecode-parity/run9/`、`logs/hwdecode-parity-r9/`。
