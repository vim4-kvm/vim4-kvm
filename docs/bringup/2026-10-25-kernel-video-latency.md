# 2026-10-25：5.15 / 7.3 视频延迟对照与 Wave5 启动修复

用户要求测量当前端到端视频延迟，并核实 7.3 是否更快；明确授权临时切换到
已安装的 7.3，测完恢复 5.15。持有 board/heavy 双锁，构建与性能采样串行。

## 测量边界与配置

  接收工具启用音频，但源端未生成音频测试信号，本次没有音频连续性验收。

## 实测发现的 7.3 回归与修复

7.3 初始 H.264/H.265 都在等待首帧时超时，底层报
`Got 2 dmabuf but needed 1`。厂商服务继承的 `GST_V4L2_PREFER_CONTIGUOUS=1`
也进入了新部署的标准 V4L2 插件，使 Wave5 编码输入选择单平面 NV12；
One-KVM 的桥接提供两个平面，导致导入失败。

主仓库 `e7ea805` 在 `board/vim4-kvm-run` 的 mainline 分支清除该变量，
厂商分支保留原行为。启动器回归覆盖四应用及 7.3 stable/rc7、继承变量的情况。
H.264 表中的 7.3 窗口先通过临时同等环境修复测得；随后删除临时配置，正式构建、
校验并部署 board / vfmcap / amlvenc `2.5.1+vim4.20261025.15`，H.265 使用正式包。
无需改动 One-KVM 二进制、GStreamer 插件代码或内核。

正式包下四应用两轮交错切换共 8 次，均真实解码 4K、约 59.98–60.49fps，
drop/lost 增量均 0；从切换请求到首帧为 8.1–13.3 秒，不代表稳态延迟。
这只覆盖四应用出图，端到端延迟表仅针对 One-KVM。
7.3 taint=0、failed units=0。
恢复 5.15 后的启动日志有厂商 DRM vblank warning，采样前 taint=12800；
不能表述为整个 5.15 启动无告警。HDMI 两个配置文件哈希与切换前一致。

启动前还发现 vendor 登记清单的最后两个 APPEND 参数顺序与实际 extlinux 不同，
导致管理器将恢复项标为不可用。核实参数集合及其他启动字段完全一致，按实际顺序
同步登记元数据，分别完整验证 vendor 1535、mainline 2349 个产物哈希后才切换。
没有更改启动参数内容或跳过完整性验证。

## 后续可验证的优化点

浏览器实测 jitter-buffer residence 约 2.50–2.83ms、平均解码约 2.11–2.92ms，
继续压缩播放缓冲的空间有限，不能仅凭目标缓冲为零推断整条链路已经最短。

基线完成后，单独临时启用 `ONEKVM_VIDEO_STATS=1`，测试 5.15 / SDR / H.264。
编码器 sink→src 的每 5 秒统计均值为 12.33–12.43ms，P50 桶上界 12.5ms、
P95 桶上界 14ms、P99 桶上界 14–15ms，peak_active=1，无直方图溢出；
稳态采集与编码进出约 60fps。原尺寸未经过独立 scaler。
这是附加诊断，不与端到端分位数相加，也不证明源队列没有等待。
立即重启服务后第一次诊断等待视频超时，无采集日志；保留该失败，服务启动稳定后
才取得上述统计。没有以该失败窗口计算延迟；后续恢复过程中也观察到短暂 HTTP 502。

厂商 `common_drivers/drivers/media/vin/tvin/vdin/vdin_drv.c` 的 `vdin_v4l2_isr`
先发布上一轮 `last_wr_vfe`，再把本轮帧存入该字段，等下一次中断交付；
普通 ISR 的 game mode 有不同交付路径。最初将这里列为可能消除一帧等待的线索，
后续[实际 RDMA 表及逐缓冲追踪](2026-10-25-vdin1-frame-handoff.md)纠正了该解释：
当前 RDMA 后端提前一拍提交地址，下一拍硬件执行，再下一拍交付完成帧。
`curr_wr_vfe` 不能当成当次中断时已完成的图像，不能直接删除 `last_wr_vfe`
交接或承诺减少 16.7ms。寄存器 DMA 完成也不是图像写完事件。

源队列、编码池的容量不是实际积压的证据；本次未盲目缩池、丢帧或降低画质。
