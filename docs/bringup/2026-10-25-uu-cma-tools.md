# 2026-10-25：UU 缩放 CMA 生命周期与工具连接

跟进 [P1 验收限制](2026-10-25-uu-p1-validation.md)：hdrdual6 缩放重配、最低 HEVC 码率及 G4 工具连接转桌面已修复并验收，合入推送 One-KVM `vim4/1c1a790d`。G2 板子文件传输仍在实施，尚未标为通过。不测声音，不保留回退副本。

## CMA 复现与确切位置

内核 `5.15.137-vim4kvm-hdrdual6`、HDMI 3840×2160@60，One-KVM 原包 `.20261025.4`。只读 RAM 分配统计、DMA-buf fd 与 GObject 销毁观察，不读取硬件寄存器。复现无需切 HDR、EDID 或重启透传服务。

原始标准 v4l2src 优先 NV21M：每帧两个 DMA 内存，Y 8,294,400 字节、VU 4,149,248 字节。One-KVM 的 VDIN1 分配预算最终得到每池 10 帧。原尺寸流水线关闭后 source/pool 可销毁；经 amlvconv 缩放的流水线关闭后，pipeline/scaler 可销毁，source/pool 却仍存活，且每轮留下整池。

板端厂商 `libgstamlvconv.so` 的 SHA256：`e34e696326c14f20d7cd0102147543ae296c0bdfddbc75c35dda1d85abe50200`。独立反汇编确认：

- `gst_aml_vconv_transform_frame`，ELF 虚拟地址 `0x2ef4`：取得输入第 1 平面（以及三平面格式的第 2 平面）的 `gst_buffer_get_memory` 引用，但出口只释放输入第 0 平面及输出内存。残留色度引用使采集池和 source 无法释放。
- `gst_aml_vconv_prepare_output_buffer`，`0x3880`：分配输出内存后未检查 NULL 就插入 buffer，并回成功。耗尽 CMA 后，变换函数继续使用不存在的输出内存，导致进程 SEGV。

未复制反编译代码、参考实现代码或厂商二进制入库。上述地址仅对应该 SHA 的故障行为。

失败现场仍有两组 VDIN1 池，共 40 个导出 fd、约 237.3 MiB；codec CMA 已用 574.7/580 MiB，最大连续块仅 535 页（2.09 MiB）。1080p GE2D 每块要 3,112,960 字节，故分配失败。不是总系统内存不足，也不是把 codec_mm 的 free 统计当作真实可分配 CMA。

| hdrdual6 消费者 | 实际占用/归属 |
|---|---|
| VDIN0 原生 HDR | 10 × 24,883,200 字节，约 237.3 MiB，codec CMA |
| 编码固件 | 4 MiB，codec CMA |
| HEVC 编码器 | 100 MiB，缩放尺寸变更仍按厂商实例预算预留 |
| VDIN1 SDR 捕获 | 一组约 118.7 MiB，来自 codec CMA；设备树名为 vdin1 的独立 60 MiB 区并未承载这些 vb2 帧 |
| GE2D 缩放输出 | 3 块，720p/1080p/1440p/1800p 每块约 1.32/2.97/5.27/8.24 MiB；原尺寸不需要 |

`codec_mm_dump` 不包含直接 vb2 CMA 分配，现场虽声称约 238 MiB free，codec CMA bitmap 已近耗尽。其他 camer/ge2d/vdin1/pcie/gfx CMA 区的空闲页不能直接补给 codec CMA，`/proc/meminfo` 的全局 CmaFree 也不能证明大块分配可成功。

## 修复与离线验证

采用驱动已支持的连续单内存 NV21，避免触发厂商缩放插件的多平面引用泄漏，仍为 DMA 传递，不增加整帧 CPU 复制。私有标准 V4L2 插件新增显式 `GST_V4L2_PREFER_CONTIGUOUS=1`：仅 raw 格式优先连续布局，硬件不支持时仍回落多平面；压缩格式保持原行为。One-KVM 服务启用该选项，构建必须带上匹配的私有插件，缺失直接报错。

应用提交 `046a355c`；主仓构建提交 `9fa1209`。现有 pool orphan 顺序修复的确定性测试能在上游原始代码复现失败，但仅应用这批旧补丁仍复现本轮泄漏，因此没有把旧 orphan 问题当作当前根因。

- 新增测试从实际打补丁后的 upstream C 中提取布局选择函数并编译，覆盖 8 种支持/偏好组合、无格式、压缩格式与回落行为；旧 orphan 协调测试同时通过。
- Cargo 离线锁文件全量：758 通过、2 忽略；Python 助手 35 通过，DMA 分配器测试、release 通过。
- 主仓 254 项：247 通过、7 跳过。正式 `.20261025.5` deb 的校验、真实升级/配置保留/更新 API 检查通过。
- 初步六次重配始终仅一组 10 个 VDIN1 fd，GE2D 始终 3 块；codec CMA 使用约 460–485 MiB，最大连续块约 93–118 MiB。无需修改内核 CMA 预留。

## 正式上板结果

全部上板操作持有 `/usr/bin/lockf /tmp/vim4-board.lock` 与 `/tmp/vim4-heavy.lock`。正式服务使用包内私有插件，已移除本任务的临时启动器。以 Mac RTK HDMI 显示器上的运动源测试，仅统计成功发送的编码帧/字节，不冒充客户端呈现帧率。内核、EDID、HDR、透传服务保持原运行实例。

`.20261025.5` 在 3840/3200/2560/1920/1280 宽度之间按有向完全图的欧拉回路重配 20 次，每一种不同尺寸之间的有向转换恰好一次。稳定采样窗口最低发送 fps 为 59.884，各尺寸均值约 60；每轮始终 10 个 VDIN1 fd，缩放时 3 个 GE2D 输出，无累积。

随后原尺寸连续 600 秒、120 个发送窗口：最低 59.934、均值 60.007fps、序号缺口 0。另对最大缩放档 3200×1800 连续 600 秒、120 个窗口：最低 59.705、均值 59.996fps。两窗口均无 CMA 分配失败、Oops/panic，应用 PID 保持不变，包校验无差异。

证据在不入库的 `logs/uu-cma/`：`formal-result.json`、逐轮 `memory-formal-*`、`scaled-stable-result.json`、发送 journal、内核日志。首轮脚本与客户端初始化设置竞争导致 API 等待超时，未计通过；原始崩溃及失败构建证据也保留。

## 1 Mbps 码控归因与修复

相同 4K60 运动源、每次预热 300 帧后统计 1800 帧；GOP 0，统计段关键帧数均为 0：

| 请求/行刷新/QP 上限 | 实测 Mbps |
|---|---:|
| 1 Mbps / 1 行 / 厂商默认 | 1.5469 |
| 1 Mbps / 关闭 / 厂商默认 | 1.0005 |
| 1 Mbps / 1 行 / 显式 51 | 1.5237 |
| 1 Mbps / 关闭 / 显式 51 | 0.9962 |
| 4 Mbps / 1 行 / 厂商默认 | 4.0015 |

解析原始 HEVC：超调段最后 1800 个 slice 的 QP 均为 51，无法再提高量化；关闭行刷新即可命中目标。由此确认主要是行刷新开销及量化上限，非单位错误、周期 IDR 或编码器固定最低 1.6 Mbps 限制。

`68c5bd18`：最低 HEVC 档（≤1000 kbps）关闭周期行刷新，保持 GOP 0、新订阅与 PLI/FIR 完整关键帧恢复；正常 HEVC 档及 H.264 保留原策略。新增配置边界回归，6 项视频测试通过。弱网恢复仍依赖显式关键帧反馈，本轮未注入丢包。

`.20261025.6` 官方 UU 连接原尺寸 1 Mbps 的 10 个发送窗口：均值 **1.0012 Mbps**，最低 **59.994fps**，序号缺口 0。

## G4 工具连接取得桌面

`1c1a790d`：工具 offer 预先协商休眠媒体轨，`capture_desktop(4)` 幂等取得同一连接的桌面角色，再订阅共享视频与启用 HID。统一控制者锁确保先松旧按键、停旧媒体，再交接；旧工具连接被接管时只失去桌面角色，终端仍可用。角色变化重发 CONTROL 初始化；关闭取消媒体任务、终端和通道回调引用。

两项真实 WebRTC 双端回归覆盖重复请求保持单一任务、终端与视频 RTP 同连接、已有桌面接管、工具退回/再次取得桌面、过期桌面关闭不影响新控制者及关闭后状态释放。全量 Rust **761 通过、2 忽略**；内部隔离网络只承载测试 ICE，Cargo 禁网、锁文件未变。

正式 `.20261025.6` 通过 deb 校验及升级/更新 API 验证，自动调用官方 `uuyc-cli term open` 后 `device connect`，确认复用工具 peer、终端 peer 保持 1，未产生新桌面 offer。1080p 缩放连续 600 秒、120 个发送窗口：最低 **59.966**、均值 **60.006fps**，序号缺口 0；二进制 SHA256 `61adf43a58b2c6137a7a0f034e764a870fbc8b5b056330566e32968786068f03`。证据为 `g4-board-result.json` 与相应 journal。
