# 2026-10-27：UU 原生 HDR 能力与非对齐行宽修复

官方 macOS UU 4.42.0 的 Main-only SDP 不代表解码器仅支持八位。
原生连接另在 `streamer_data.device_capability` 提供解码位深、尺寸和显示器能力。
接续[全局 HDR 默认](2026-10-26-hdr-global.md)，本轮接通这些声明，并修复
MacBook 开启 HDR 后停在首帧的可复现编码器故障。

## 能力与会话

One-KVM 读取对应 ICE 会话的原生能力，只有有效 HEVC、10-bit、4:2:0 且尺寸足够时，
才允许 Main SDP 的原生 UU 会话接收 Main10；不修改 SDP、payload type 或浏览器协商。
零尺寸的解码项表示不支持，缺失/无效声明不授予此能力。
显示器 `hdr=0` 表示支持、`-1` 表示不支持，不是当前 HDR 开关。
被控端同时声明八位与十位能力；不再用 `hdr=1` 表示已开启。

新桌面会话先输出 SDR，客户端明确请求 `enable_hdr` 后才临时切换。
明确声明显示器不支持 HDR 时拒绝开启；断开或被接管仍恢复最新全局默认，
不保存 UU 的临时开关，不改尺寸、帧率、码率或 EDID。
官方 SDK 的能力判定、关键帧解码器重配和 Metal EDR 分支通过只读二进制调查确认，
没有修改官方程序。用户已确认 MacBook Pro M3 Pro 的 HDR 菜单可开启。

## 首帧停住的复现与修复

停帧前日志出现 Main10 输出尺寸 3022×1700，随后编码无输出，
`VPU_EncOpen` 出现超时；切回 SDR 和重启应用未能恢复，重启板子后恢复。
仅凭日志里的 `raw=None` 不能确定采集停止：厂商后端没有启用该原始帧计数器。

停止应用，用真实私有 SDK、P010 测试源隔离编码器：

| 输入尺寸 | 修复前结果 |
|---|---|
| 1920×1080、3008×1696、3024×1696、3024×1700 | 各完成60帧并正常退出 |
| 3022×1700、3022×1696 | 首帧编码失败，退出超时 |

SDK 仅把 HEVC 高度向上对齐八像素后写入硬件，行宽仍写可见尺寸。
修复同时对齐行宽并设置右侧 conformance crop，保持请求的可见尺寸。
只增加裁剪、未修硬件行宽的第一版候选仍失败，已弃用。
修复位于 `gst-plugin-venc/hdr/p010-cpu-input.patch`，由原有固定源码构建流程应用；
不改内核或原系统八位 SDK。

完整往返又复现旧八位HEVC库的相同行宽限制。它的二进制SDK未替换，
One-KVM在该路径将缩放行宽向下取整到十六像素边界，
同时满足HEVC八像素块与GE2D紧密NV12行的16-byte DMA pitch约束。
3016宽的CPU测试虽通过，实际DMA回归仍被SDK拒绝，不能用CPU测试代替。
同一1700高度的HDR保留3022宽，SDR实际编码3008宽，实际尺寸从编码caps上报。
JPEG和H.264仍保留原来的二像素行宽策略。

候选 3022×1700 完成60帧、正常退出，ffprobe 实际解码60帧，尺寸仍为3022×1700，
Main10/yuv420p10le、PQ/BT.2020 均正确。五组硬件像素回归覆盖640、656、638、642、640宽，
每组30帧，实际尺寸正确、输入未修改，Y/UV PSNR 最低57.58dB，交替八位/十位及重开通过。

## 验证与部署

内核仍为 `5.15.137-vim4kvm-hdrdual6`。已部署 One-KVM `8954e1d3` 和
编码器 `e637980` 的两份私有 SDK 库。
Chrome 网页4K PQ连续10秒解码601帧，约60.06fps，Main10、PQ、BT.2020正确。
这证明视频持续解码，不代表 MacBook 的 HDR 光度或光学端到端延迟。
HDR 缩放仍使用 CPU，不能把原尺寸4K60结果套用到3022×1700等缩放路径。
后续[GPU缩放修复](2026-10-27-uu-hdr-scale.md)替换该慢路径，并单独复测缩放与原尺寸。

VIM4 Rust全套789通过、3忽略；UU定向108通过、2忽略；release构建通过。
编码插件离线 DMA 生命周期与公共源测试通过，固定 SDK 重新构建通过。
UU 硬件回归使用真实PQ输入，分别检查控制请求、SPS和连续完整RTP帧；
原来720p只检查一个关键帧的测试不足以覆盖本次问题，已升级到4K与非对齐尺寸。
最终69.26秒回归通过：4K的SDR→HDR→SDR→HDR各收到240个完整RTP帧，
1700高的HDR→SDR→HDR各收到30帧，同一Peer保持连接；接管和断开恢复全局默认通过。
这是调试构建接收端，不作为60fps或真实客户端解码性能基准。
MacBook 修复后的实际持续显示仍需用户复验，不以模拟接收端替代。
主仓库离线282项通过、跳过7项，Linux部署回归35项通过。
测试后恢复Mac源端原来的SDR偏好；全局HDR默认与203/1000曲线保持原值，
HDMI服务配置、EDID和输入尺寸保持原值。
