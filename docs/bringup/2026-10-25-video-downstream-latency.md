# 2026-10-25：交帧之后的编码、发送与浏览器分段

本轮只定位 KVM 在驱动交帧之后的成本。5.15 / One-KVM / SDR 4K60 / 30Mbps 下，
驱动交帧到浏览器提交合成器的同帧中位数约 H.264 17.92ms、H.265 18.56ms。
主要成本是编码完成中断等待约 12–13ms，以及随 RTP 包数增长的发送耗时。
没有发现后半程固定多等一个 16.7ms 帧周期的证据；尚未实测 HDMI 线上像素到达和
客户端面板发光，不能将这里的约 19ms 均值称为完整 KVM 光学端到端延迟。

## 条件与样本

- 内核 `5.15.137-vim4kvm-hdrdual6`；One-KVM `f037159f`、包 `.20261025.14`；
  capture / encoder / board `.20261025.15`，manager `.20261025.18`。
  原生 VDIN1 NV21 DMA-buf → amlvenc → parser → appsink → WebRTC。
- Chrome `156.0.8078.47`、headless 独立上下文、单观看者；物理 RTK HDMI 测试屏持续运动，
  上中下三处像素 ID；SDR、3840×2160、60fps、自定义 30000kbps，未改 EDID/HDR/HDMI 服务。
  音频配置保持 enabled，协商包含 Opus；本轮没有独立测音频质量或延迟。
- 板端 eth0 `192.168.50.210` ↔ Mac en0 `192.168.50.239` 的 LAN UDP 媒体，
  HTTP 经 SSH 转发。预热视频 15 秒、像素 3 秒；构建和其他浏览器验收与性能窗口串行。
  测完恢复原 H.265 配置，再允许另一任务做本机构建；离线解码在性能窗口之外进行。
- H.264 深分段：120.004 秒、1023 个浏览器像素样本、实收 30.059Mbps。
  H.265 深分段：90.002 秒、842 样本、30.099Mbps，仅用于诊断均值/P50/P95。
  H.265 对照：120.001 秒、1181 样本、30.109Mbps，关闭 Chrome trace 和双端抓包，保留板端探针。
  H.265 的 90 秒窗口不足[验收协议](../latency.md#测量有效性与接受改动的规则)的
  120 秒/1000 标记门槛，不能拿它宣称 P99 达标。

## 同帧关联与探针边界

在[已有分段](2026-10-25-video-stage-latency.md)上扩展临时 `LD_PRELOAD` 诊断，
按 GstBuffer PTS 关联 `amvenc_encode` 入口/返回和 `/dev/amvenc_multi` 的 ioctl。
按 SSRC、RTP 时间戳、包序号、实际头长及完整 payload 长度序列唯一关联发送 AU。
没有映射原始像素 DMA，没有访问 MMIO，也没有改动厂商编码库、编码参数或生产二进制。

所有采样完成后离线解码 8925/7254/8497 个 H.264/H.265/H.265 对照 AU，
全部三带 ID 校验有效。H.264 的 1023 个浏览器样本中，有 4 个实际读到下一帧像素，
与回调 RTP 时间戳对应 AU 的 ID 差 1；保留在 `down-h264.rejected.json`，不作同帧拼接。
最终有效配对为 1019/842/1181，其他两个窗口无关联拒绝。以下 H.264 分位数均使用
1019 个已独立核对像素的样本。全部最终 SSRC 发送帧 8702/6870/8116 均唯一匹配 AU。

编码 API 的 `WAIT_INTERRUPT` ioctl 在驱动中执行 `wait_event_interruptible_timeout`。
这段包含等待完成中断和线程唤醒，不能进一步声称已经测到纯硬件启动到完成：
厂商库直接写命令寄存器的时刻尚未打点。插件 API 返回后的分配/码流复制另列。

浏览器 trace 用同一 RTP 时间戳关联 Mojo 解码提交、GPU 进程 Decode、GPU 输出及
renderer 收到解码帧。所有解码输出均标记 `VideoToolboxVideoDecoder`、OPAQUE NV12，
确认走硬解码。`performance.mark` 将 trace 时钟与页面单调时间对齐。
终点为 rVFC `presentationTime`，即提交合成器；`expectedDisplayTime` 不作为实测发光。
时间戳语义见 [rVFC 草案](https://wicg.github.io/video-rvfc/)；浏览器时间精度限制使
极小的“解码交还→提交”差值可能略小于零，应解释为接近分辨率。

## 发送、网络与浏览器

H.264 发送段 P99 10.641ms；H.265 的 120 秒对照为 8.576ms。
同帧发送时长与包数的相关系数分别为 0.998、0.997；120 秒对照 H.265 每帧平均
49.6 包，H.264 为 48.4 包。每帧包数/字节数 P95：H.264 为 182 包/约 220KB，
H.265 对照为 140 包/约 170KB。这些已采样大帧都是 P 帧，不能归因于定期 IDR。
H.264/H.265 深分段平均发送系统调用合计 0.991/0.962ms，调用间隙合计
1.453/1.456ms；后者仍包含协议/加密/调度及逐包探针，尚不能全算成线程空等。
包数与字节数的 P95 是各自分位数，不代表同一指定帧。

双端以同一 `(SSRC, RTP timestamp, sequence, UDP length)` 核对 RTP 包：
板端 AF_PACKET 用内核 `SO_TIMESTAMPNS`，Mac 用 en0 BPF/tcpdump。
板端点是内核出包观察点，不是物理网卡出线；Mac 点是内核收包观察点。
20Hz UDP 请求/响应校时将板端 MONOTONIC 映射到 Mac，使用相邻有效交换插值。
深分段样本的半 RTT 平均约 0.43ms，最大约 0.65ms；加上页面 Date 量化后，
驱动到页面终点的跨设备不确定度最大约 1.65ms。

网络约 0.25ms 的估计小于校时不确定度，不能宣称精确亚毫秒测量。
逐帧加半 RTT 后，网络估计上界最大分别约 0.99/0.95ms；此界仍依赖端点时间戳定义。
首行有最低 -0.021/-0.011ms 的时间映射误差，故只作量级判断。
Mac 内核收包到 rVFC receiveTime 的原始均值为 -0.425/-0.470ms，处于页面与内核
时钟映射及浏览器精度限制内，这一小段尚不能可靠单独分离；不报告物理负延迟。
`processingDuration`、getStats jitter residence 与上述浏览器链路重叠，不另行累加。

## 优化优先级与恢复

1. 优先验证每包发送路径的优化。本轮尾部与同帧包数高度相关，代码逐包 await RTP 写入；
   应进一步拆分分包、SRTP/拦截器及 socket 写入，评估减少逐包分配/调用或合适的批处理。
   这是候选方向，尚未实测收益；不能通过降码率、画质或擅自扩大 MTU 宣称无损优化。
2. 编码约 12–13ms 是最大确定成本，但 DMA 映射/缓存/码流复制分别只有几十微秒。
   缩 appsink/采集池不能去掉这段中断等待；厂商库内部启动、硬件与唤醒仍需更细打点。
   不采用已出现码流不确定的[750/800MHz 超频](../encoder-experiments.md#超频正确性)。
3. 浏览器解码前等待 P95 约 3.8ms，H.264 硬解码输出尾部也高于 H.265。
   可以继续做无像素回读/不同显示模式的接收端对照；目前不是稳定多缓存一帧的证据。
4. 网络估计不足 1ms、驱动交帧到编码约 0.2ms、解析/取帧约 0.2ms，当前优先级较低。
   采集交付之前仍遵循[前段边界核实](2026-10-25-video-front-boundaries.md)，
   不把 Mac 源端显示排队当成 KVM 可以优化的延迟。
