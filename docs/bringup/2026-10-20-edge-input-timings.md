## 实现与回归

RX 从参考时钟计数器读取帧周期，连续两次读取不同则返回 `EAGAIN`，避免按字节
读取时拼成错误周期。失锁、隔行、非 RGB8、未支持的尺寸/总周期/同步宽度均拒绝；
不返回旧缓存。只有固定 CEA 配置匹配时才使用其 porch/polarity 描述，pixelclock
按实测周期计算，不把 59.94 当成精确 60。`G_PARM` 不声明可设置源帧率。
查询函数没有 20ms 帧间等待，也不重配 PHY、DMA、EDID 或 HPD。

首次上板查询全部 `ERANGE`，原应用仍能正常播放。只读核对实际寄存器发现：
`0x1890/0x1892` 为水平低/高电平计数 `4312/88`，`0x1898/0x189a` 为垂直
低/高电平计数 `2240/10`；正同步脉冲必须读取高电平计数。修正寄存器命名、
夹具及查询，并增加反极性拒绝回归；原来总计数相加的采集判定不受影响。

内核 core/DDC/PHY/link/audio/VDIN/stream/timings 八组回归通过，新增实际 C 夹具
覆盖 FHD/UHD、60/59.94、跨更新计数器、失锁和未支持模式；使用 Linux UAPI
头及 ASan/UBSan，驱动目标和完整内核/模块构建通过。One-KVM 721 通过、2 忽略，
修改文件 rustfmt 与 ARM64 release 构建通过。59.94 和 FHD 仅夹具验收，本轮未改变
真实 HDMI 输出模式；不声称已完成任意分辨率/帧率/颜色格式支持。

## 板上结果与限制

当前输入 3840×2160、总周期 4400×2250，周期 `2777825/166666664` 秒，
pixelclock 593989892Hz，API 帧率约 59.998979fps。原生连续 1000 次查询零失败，
QUERY 平均 0.020080ms、最大 0.118501ms；这是空闲状态的查询耗时，不是视频延迟。

新应用短测：H.265 59.972fps，H.264 59.970fps，均为原生 3840×2160，
10 秒采样内丢帧、丢包及 freeze 增量为 0。显示休眠 4 秒造成真实失锁，原 H.265
网页连接不刷新自动恢复，SSRC 保持；恢复后 5 秒 59.975fps，输入 API 恢复锁定。
并行 60 次时序采样中有 18 次失锁错误返回，不把缓存报告成锁定。恢复后 H.264
网页解码 HDMI-only 440Hz 测试音峰值 0.101715。没有外放或 HID 输入注入。
结束时实验应用、网关和 USB 服务 active，无观看者，DMA-buf=0、VDIN faulted=0、
taint=0，CMA 空闲 505192KiB；50.5°C 时风扇控制值为 16%。

失锁测试同时暴露队列锁限制：一次查询等待约 978ms。新增查询函数本身不等待帧，
但 V4L2 ioctl 仍与 DMA 停流共用锁；本轮保留现有锁和缓冲生命周期规则，没有将
空闲查询耗时当作失锁时上限。后续队列重配需要一起解决这段阻塞。
后续已拆分两类锁并完成同场景复测，见 [队列锁修正](2026-10-20-edge-queue-lock.md)。

尚需增加 source-change 通知、受支持模式选择、停流后安全重分配和应用重建链路，
才能验收 1080p ↔ 4K 自动切换；YCbCr/HDR、不同帧率的 PHY/audio 重配也未完成。
本轮不是物理拔线、整机休眠或长时耐久验收。
