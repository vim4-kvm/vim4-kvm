# 2026-10-15：UU 虚拟屏恢复故障定位

用户重发 EDID 恢复后再次用真实 UU 客户端复现。只读检查确认板端仍接收
4K60 YUV444 8bit 且帧数推进，Mac 在线列表仅有系统兜底 ID 44；RTK 物理 ID 2
无法通过公开显示 API 查询。UU 4.42.0 的 UURemoteServer 创建“UU远程 1”
后约 0.43 秒销毁，随后 WindowServer 生成兜底屏。

ARM64 静态分析确认 UU 的 restorePhysicalModes 路径只遍历在线显示器，
不能处理已不在线的物理屏；模式设置函数另有忽略单步错误返回的局限。
尚未确定最初掉出在线列表的触发点，不能直接归结为 UU 缺少所有恢复逻辑，
也不能把热插拔有效当成 EDID 内容错误。详见 [调查记录](../hdmi-uu-recovery.md)。
本轮未修改 Mac 显示配置、未重发 EDID、未停启服务，故障现场保留。

后续只读解析 UU 加密 MMKV，发现最近使用的控制端配置保存着“UU远程 1”
（slot 1、1×1、60Hz、非 HiDPI），其他两个控制端配置没有虚拟屏记录。
保存时间早于本轮测试。连接路径可在有物理屏时恢复历史虚拟屏；运行日志显示
UU 请求 1×1 的 unsupported mode 86 后立即销毁虚拟屏，与异常记录吻合。
尚未清除该记录或完成对照，暂定为最强触发候选，不能声称因果已验证。

随后用户授权不备份直接删除：停止 UU 用户写入进程后仅清空该控制端的
异常虚拟屏条目，逐字节验证其他 MMKV 记录未变，更新并验证校验信息。
UU 用户代理及应用已重新启动；读回 virtualDisplays 为空，83 条显示信息保留。
未重发 EDID，同一控制端重连的恢复验收仍待完成。

清理后用户反馈“现在可以了”，支持异常历史虚拟屏配置为本次 UU 故障的
触发因素。尚未采集清理后的完整日志或进行重复回归，记录的生成原因待查。
