## 根因与消融

1. **共享时钟被编码器降频。** T7 GE2D 的驱动配置为 667MHz，启动日志实为
   666MHz；运行时却为 399999994Hz。对单独 tracefs instance 的时钟事件做
   三秒定向记录，调用栈明确落在 `vpu_open → clk_set_rate`；不是 ptrace，
   该短窗口不用于帧率验收，记录结束立即删除 instance。
   `drivers/media_modules/frame_sink/encoder/multi/vpu_multi.c::vpu_clk_enable`
   给 `dos_apb_clk` 固定请求 400MHz，而 `mesont7.dtsi::aml_enc` 的
   `clk_apb_dos` 绑定的是 `CLKID_VAPB`，正是 GE2D 的共享父时钟。
2. **同步串行管线。** 原管线在一次 streaming thread 中完成缩放后再编码，
   无跨阶段并行。仅增加一个非丢帧有界队列，1080p 从约 34 提高到约 40fps，
   但 GE2D 仍受 400MHz 限制，不能据此声称已修好。
3. **逐帧 DMA 分配。** amlvconv 的 prepare_output_buffer 每帧新分配 heap-codecmm，
   而不是复用空闲输出。1080p 分配约 1.6ms，更大输出成本更高。
   仅复用不能解决 400MHz 下的 blit 吞吐，仍必须恢复时钟及跨阶段流水线。

内部诊断将 `aml_ge2d_process` 进一步分解：1080p 的 CONFIG_EX_MEM 约 30µs，
阻塞 STRETCHBLIT_NOALPHA ioctl 约 22.5ms。不是 22ms 的 DMA 导入或用户态同步。
库虽导出额外 dmabuf 同步函数，但这条 process 调用链未调用它们；不能据符号存在猜根因。
恢复时钟必须发生在编码器已打开之后：在启动管线之前设 666MHz，会再次被 vpu_open
覆盖，早期这种对照已作废。正式消融在预热后设置并核验实际 666666656Hz。

| 消融，透传开启 | 1800p | 1440p | 1080p | 720p |

## 硬件方案核查

- **7.3 已有路径：** One-KVM Wave5 后端令 V4L2 采集输出目标尺寸，T7 VDIN
  H/V scaler 在 MIF 写内存前缩放，再通过两平面 DMA lease 交给 Wave5 编码器，
  不经过这里的 GE2D。VDIN 配置见内核 `t7-vdin-test.c` 的 HSC/VSC phase step。
  每帧没有独立用户态缩放调用，不能将 16.67ms 帧周期写成缩放耗时或宣称耗时为零。
  [既有缩放记录](2026-10-21-edge-scaling-jpeg.md)曾测 4K/1080p/720p 约 60fps，
  本任务未重启到 7.3，历史记录不是本轮重新通过。
- **5.15 VDIN0：** 厂商 V4L2 start_tvin 能把目标大小交给 `prop.scaling4w/h`，
  因此关闭透传后有直接前级缩放的实现基础。但现有 vfm_cap/透传共享 VDIN0
  的同一批 vframe，直接缩小会同时降低 VD1 透传画质，不能作为常开修复。
- **5.15 VDIN1：** 当前 `/dev/video71` 枚举的是 VIU writeback 输入，不暴露 HDMI RX；
  vdin_v4l2_start_tvin 对 index 1 还使用 loopback 格式路径。硬件 mux 有 HDMI 选择
  不等于当前驱动已提供安全双采集 API。T7 两路 `vdin_get_port_type` 都为 MAIN
  （仅 T3X 的第二路为 SUB），共用 RX frontend；关闭一路会关闭 main_port、音频 PLL
  和 RX IRQ。缺少引用计数/生命周期隔离，未强行启动双路破坏正在使用的透传。
  AFBC + double-write 也不是任意尺寸独立输出的现成用户态合同，未在本任务启用。
- **编码器输入缩放：** amvenc 公共 frame_info 有 scale_width/height，但已安装库的
  multi/Wave521 分发函数不读取这些字段；不能因为头文件有字段就声称支持。
- **本候选：** 保留纯硬件 GE2D + Wave521，保持 NV21 → NV12 的既有 DMA 路径，
  不改用 CPU videoscale，不改变 VDIN0、内核、设备树或默认启动项。
