# 2026-10-25：One-KVM 同帧分段延迟

当前 5.15、SDR 4K60 / 30Mbps 下，同帧测得编码平均 H.264 12.31ms、H.265 13.06ms；
驱动交帧到编码入口约 0.20ms，未发现这里存在整帧积压。
最大的未拆分部分是源端绘制到采集交付，包含 Mac 显示输出及 HDMI 采集，
不能全算成驱动等待。网络最后一包传递接近校时分辨率，不能报告负延迟。
后续[显示与采集边界核实](2026-10-25-video-front-boundaries.md)加入内核 kprobe 与
WindowServer 显示时间，并区分首次采到新 ID 与重复画面的年龄；旧 35/52ms 两档仍未全部定因。

## 配置与测量边界

  capture / encoder / board 包 `.20261025.15`。本次不切换内核、不替换应用二进制。
- VDIN1 `/dev/video71` → NV21 DMA-buf → 厂商 amlvenc → parse → appsink → WebRTC。
  原生 3840×2160、60fps、自定义 30000kbps；实收 H.264/H.265 30.061/30.078Mbps。
  当前输入为 SDR、YUV444 8bit、约 59.99Hz，未改变 HDR/EDID 或透传设置。
- Chrome `156.0.8078.47`，独立测试上下文、单观看者；运动网格和上中下三个像素帧号。
  Mac `192.168.50.239` ↔ 板 `192.168.50.210`，媒体直连 LAN UDP，板端 eth0；
  HTTP 使用 SSH 转发。每轮视频预热 15 秒、像素预热 3 秒后记录 120 秒。
- 软件端点为源端 NSView 开始绘制到浏览器提交对应帧给合成器；未测面板发光。
  [前次内核对照](2026-10-25-kernel-video-latency.md)仍是独立实验，不能混合分位数。
- 持有 board/heavy 双锁。与另一项已授权 manager 部署错开性能窗口；
  H.264 窗口 manager `.16`，H.265 补测 `.17`，各自采样期间没有构建、部署或页面巡检。

## 同帧关联与误差

临时 `LD_PRELOAD` 库只为 One-KVM 注册 GStreamer buffer pad probe，并观察
`gst_app_sink_try_pull_sample`、成功的 V4L2 DQBUF 和发送系统调用。固定长度二进制
事件及编码 AU 写入 `/tmp`；不映射原始图像、不访问 MMIO、不修改 DMA/RDMA 控制。
临时 systemd drop-in 启用诊断，结束移除并重启回原服务。

1. DQBUF 的 MONOTONIC 时间戳来自 `vdin_v4l2_if_isr` 在 `vb2_buffer_done` 前的
   `ktime_get_ns()`，是驱动交帧时间，不能当 HDMI 像素到达时间。
   全部 DQBUF 与 source pad 事件顺序一一对应，最大间隔 H.264/H.265 为 0.367/0.480ms。
2. source、encoder sink/src、appsink sink、应用取帧按唯一 GstBuffer PTS 关联。
   两轮分别 8818/8982 帧，所有阶段数量相等；编码器同时在途峰值均为 1。
3. 按最终协商 SSRC 筛选网络事件，检查 RTP 序号连续和每帧最后一个 marker；
   以完整 RTP payload 长度序列唯一匹配对应 AU，扣除实际 RTP 头及 10-byte SRTP tag。
   两轮各 8595 个已发送 RTP 帧全部唯一匹配；其余采集 AU 不直接判为视频丢帧。
4. 全部性能窗口完成后，在 VM 用 FFmpeg 6.1.1 离线解码保存的 AU：8818/8982 帧
   全部三处帧号一致、校验有效。再用浏览器 `rtpTimestamp` 和像素 ID 独立核对，
   H.264 1113/1113、H.265 1108/1108 个样本全部匹配，无拒绝或相邻帧误配。
5. 通过持续 SSH 请求/响应将板端 MONOTONIC 映射到 Mac Date 时钟，使用前后相邻的
   有效探测插值；过滤启动及 RTT>4ms 的交换，不直接相减两个设备的系统时间。
   加上浏览器逐样本时钟映射误差，同帧跨设备分段的不确定度最大 1.82/1.74ms。

浏览器 `receiveTime` 表示该帧最后一包到达，`presentationTime` 表示提交合成器；
`processingDuration` 为送解码到帧就绪的处理时间，可能包含 GPU staging。
语义依据 [rVFC 草案](https://wicg.github.io/video-rvfc/)。
未用 RTCP 推算的 `captureTime` 冒充真实 HDMI 采集时间。

## 分段结果

单位 ms，表内每格为 **均值 / P95**；每种编码均使用上文同一配对样本集合。
不同分段的 P95 不能相加。板内分段共用 MONOTONIC；首段和网络段另受上述校时误差影响。

| 分段 | H.264 | H.265 |
|---|---:|---:|
| 源端开始绘制 → 驱动交帧 | 44.650 / 52.366 | 49.616 / 49.757 |
| 驱动交帧 → DQBUF 返回 | 0.067 / 0.096 | 0.064 / 0.097 |
| DQBUF 返回 → source pad | 0.044 / 0.061 | 0.041 / 0.054 |
| source pad → 编码入口 | 0.094 / 0.206 | 0.097 / 0.201 |
| 编码入口 → 编码输出 | 12.305 / 13.453 | 13.061 / 13.792 |
| 编码输出 → appsink 入口（含解析） | 0.139 / 0.238 | 0.121 / 0.189 |
| appsink 入口 → 应用取帧 | 0.075 / 0.183 | 0.062 / 0.169 |
| 探针保存 AU 的附加耗时 | 0.145 / 0.396 | 0.116 / 0.200 |
| 保存结束 → 第一次发送调用 | 0.725 / 2.016 | 0.619 / 1.253 |
| 第一次发送调用 → 最后一包发送返回 | 2.221 / 7.438 | 2.268 / 5.494 |
| 最后一包发送返回 → 浏览器收齐 | 接近校时分辨率 | 接近校时分辨率 |
| 浏览器收齐 → 提交合成器 | 3.148 / 6.500 | 2.546 / 5.600 |

网络段原始均值分别为 -0.177/-0.173ms，最小值 -0.867/-0.899ms，处于校时误差内；
不能解释成物理负延迟或承诺精确到亚毫秒。该段还包含内核发送队列、网卡及接收调度，
发送返回也不是网线上的最后一个 bit。原始估计保留，不以钳零后的值计算“优化收益”。

同帧软件端到端均值为 63.44/68.44ms，中位数为 **67.28/67.84ms**。
首段 H.264 中位数 52.04ms，样本集中在约 35ms 和 52ms 两带；H.265 中位数 49.59ms。
源端显示相位未保持一致，不能用均值差宣称 H.264 比 H.265 快 5ms。
`processingDuration` 采样均值 2.58/1.98ms 是浏览器末段内的辅助统计，不另行叠加；
getStats 实际 jitter residence 约 2.97ms，也与收包/解码阶段重叠，不能重复计时。

| 实际编码 / 窗口 | 有效像素样本 | 端到端 P50 / P95 / P99 (ms) |

| H.264，分段探针 | 1113 | 67.28 / 78.96 / 84.05 |
| H.264，恢复后无探针 | 1115 | 67.13 / 77.78 / 80.79 |
| H.265，补测分段探针 | 1108 | 67.84 / 73.35 / 77.23 |
| H.265，恢复后无探针 | 1049 | 67.42 / 73.72 / 76.73 |

全部有效窗口约 60fps，浏览器 dropped/lost/freeze 增量、无效/不一致帧号均为 0。
第一轮基线为 H.265，但应用重启后回落 H.264，故不能将其当 H.264 探针前对照。
补测 H.265 时一次启动后 API 502，编码设置未生效；新增 `--expect-codec=h265`
实际拒绝了 H.264 窗口，未计入结果。等 API 就绪、显式设 H.265 后重新完整采样。
测量器现在记录实际 codec、RTP 时间戳和 receiveTime，并在测量前后检查预期编码。

保存 AU 的开销单列，但 pad/每包记录也有开销，未全部剥离。相同编码的有/无探针
P50 分别差 0.15/0.42ms，P95 差 +1.17/-0.36ms；这些单轮对照不能证明零扰动，
也没有完成三组 A/B/A、长时间耐久或等画质评估。不能从端到端值简单扣掉探针时间
就称为生产真实延迟。

## 优化含义与收尾

先进一步拆分源端显示输出与采集完成边界；目前不能确定 35–52ms 首段中哪些属于
Mac 合成/扫描、HDMI RX 或采集交付，也不能据此删除一帧。
关于 `last_wr_vfe` 的约束仍以[实际 RDMA 追踪](2026-10-25-vdin1-frame-handoff.md)为准。
编码 12–13ms 是明确成本；发送段 P99 为 H.264 11.01ms、H.265 7.89ms，值得定位尾部。
原始队列约 0.1ms、appsink 等待不足 0.1ms 的均值不支持盲目缩池或把 timeout 当固定等待。

恢复 5.15 / SDR / 原尺寸 60fps / 30000kbps / H.265，视频和 stream 配置与进入窗口时相同；
未变更 UU 配置。临时库、数据、drop-in 均从板上删除，运行进程无探针映射；
测试浏览器、运动源、校时进程、HTTP 转发关闭，双锁释放。One-KVM PID 20762、HDMI PID
1094，manager PID 18304，服务 active、failed units=0、WebRTC session=0。
taint 保持厂商启动后的 12800，窗口期间未新增 Oops/BUG/WARNING；不撤销既有启动告警。

本地忽略目录保留 `logs/segment-*` 基线/探针/对照、源帧、校时、诊断 C/Python、失败记录，
`logs/vim4-segment-14674.*` 与 `logs/vim4-segment-h265-20301.*` 保存事件、AU、离线标记、
同帧配对及分段 JSON。离线完整校验与测量器语法检查见本次提交说明。
