# 2026-10-23：U-Boot framebuffer 的 simpledrm 接管实验

本轮实验针对已接 HDMI-OUT 采集卡、没有 MIPI 屏的 pd-handoff 启动配置。
源码核对及板端只读寄存器证明：串口打印的 `0x3f800000` 是双 logo 区域起点，
最终 OSD1 扫描地址实际为 **`0x3fdeec00`**；不能直接把前者填进 simple-framebuffer。
候选已在采集卡实测 Linux 控制台、24bpp 色条和 4K60 双编码；48 kHz 音频通过，
44.1 kHz 旧观察器在候选和基线均失败，首轮已恢复；后续见
[音频复核及正式部署](2026-10-23-display-m0-deploy.md)。

## 厂商布局及当前硬件读回

以下路径相对上述 U-Boot worktree：

| 证据 | 结论 |
|---|---|
| `board/khadas/configs/kvim4.h:171–179` | display_bpp=24、display_color_index=24，fb_width=1920、fb_height=1080 |
| 同文件 `CONFIG_DUAL_LOGO:329–352`；`cmd/amlogic/cmd_osd.c:237–299` | HPD 高时先创建 viu2_osd0/VPP1 帧，再创建 osd0/VPP0 帧 |
| `drivers/amlogic/media/osd/osd_hw.c:1688–1725,1944–1954` | 每 VPP 一帧，第二帧偏移为第一帧长度；T7 使用线性 MIF 地址 |
| `drivers/amlogic/media/osd/osd_fb.c:124–139,550–592` | color index 24 为 RGB888，内存小端 B/G/R，匹配 DT 的 `r8g8b8` |
| `osd_hw.c:1291–1352,1635–1685` | stride 用 16 字节单位，并按 64 字节对齐；1920×3=5760 已对齐 |
| `osd_fb.c:1587–1627`；`vout/vout.c:635–641` | outputmode 改输出尺寸和 scaler window，常规 fb_width/fb_height 保持固定 |

板端只用 `/dev/mem` 的只读 mmap 读取厂商 register.h 定义的 OSD 字段，没有写寄存器。
日志 `logs/display/m0/baseline-osd-registers.log`：

```text
OSD1 CTRL_STAT 0x072ff005
OSD1 BLK1_CFG_W4 0x03fdeec0 -> base 0x3fdeec00 (寄存器单位16字节)
OSD1 BLK2_CFG_W4 0x00000168 -> stride 5760
OSD1 BLK0_CFG_W1 0x077f0000 -> x=0..1919
OSD1 BLK0_CFG_W2 0x04370000 -> y=0..1079
OSD3 BLK1_CFG_W4 0x03f80000 -> base 0x3f800000
OSD3 BLK2_CFG_W4 0x00000168 -> stride 5760
```

每帧 `1920*1080*3 = 6,220,800 = 0x5eec00` 字节；两帧末端为 `0x403dd800`
（不含）。OSD virtual height 为 2160，但当前 pan/window 只扫描首个 1080 行；
没有用户态翻页，本实验不开放硬件 pan。候选保留 `0x3f800000 + 0xc00000`，覆盖双帧
及尾部对齐空间；simplefb 的 reg 只描述实际 OSD1 单帧。

用户提供的 `logs/display/reboot2-uart.log` 中 `mipi_lcd_exist: 0`、HPD 高、VIC16、
1080p60、444/8bit；`reboot-uart.log` 为 2160p60、422/12bit。该输出色彩属性描述
HDMI 链路，并非 framebuffer 的像素格式。既有采集 `frame-489.png` 为完整 Khadas logo。

4K HDMI 时仍由固定 1080p RGB framebuffer 经 scaler 放大，simpledrm 应向用户态报告
1920×1080，不应伪称原生 4K 模式。MIPI 检测及可变 U-Boot 环境可能改变布局；静态
DTB 只适用于本次匹配条件，不能用于任意启动环境。生产方案应由 U-Boot 根据最终
`osd_hw.fb_gem[OSD1]` 和颜色表填充 `/chosen/framebuffer`、同步保留内存，并在无有效
输出时禁用节点；本轮禁止刷固件，不实现和部署该固件改动。

## 时钟、电源和内存边界

厂商 `drivers/amlogic/media/common/vpu/vpu.c` 的 vpu_data_t7 使用
`CLKCTRL_VPU_CLK_CTRL`、`CLKCTRL_VAPBCLK_CTRL`，`vpu_ctrl.h:207–212` 列
VPU_HDMI、VI_CLK1、VI_CLK2，`vpu_power.c:264–286` 用安全电源调用维持这些域。
厂商 5.15 `common_drivers/drivers/power/sec_power_domain.c` 的 T7 表也将三域常开；
与[显示硬件明细](2026-10-23-display-hardware-audit.md)核对一致。

U-Boot `arch/arm/mach-meson/t7/hdmitx_clk.c:504–548,603–757` 进一步设置
HDMI_SYS、HTX_PRIF/200M、HDMI_VID_PLL divider、VID_CLK0、ENC0_HDMI 的
pixel/FE/PNX 分支、PHY TMDS/FIFO，并清除 `PWRCTRL_MEM_PD11[15:8]` 的 TX
存储器掉电位。它们不是可以只靠 VPU 时钟替代的同义项；本轮保持启动固件留下的设置。

候选引用 VPU、VAPB、SYS_VPU_INTR、SYS_HDMITX_APB、HDMI_PLL 和上述三个域，
由 simpledrm 获取引用；不设置频率、parent，不复位 VPU。7.3 已有三个域的
GENPD_FLAG_ALWAYS_ON，HDMI PLL DCO 已有 CLK_IGNORE_UNUSED。
VID_CLK0/ENC0_HDMI 的像素分频由 U-Boot 留置，当前 T7 CCF 未完整建模，
本实验不能据此声称实现了完整输出时钟生命周期或模式重配。

保留 `&vpu` disabled，避免 native meson DRM 与 VDIN 同时申请 `ff000000/0x40000`。
simpledrm 只映射帧内存，不接管 VCBUS、scaler、TX、HDMI 音频或热插拔。

cmdline 的 `cma=512M@0x10000000-0xf0000000` 是分配允许区间，包含 logo 地址；
不能用区间字符串证明不冲突。reserved-memory/no-map 会先占用双帧区域，
CMA 应另选可用连续区。当前基线 dmesg 实际为 `Reserved 512 MiB at 0xbf000000`，
与显示区不相交。候选也在同一地址取得 512 MiB CMA，iomem 单独保留显示区，
4K60 实际采集分配通过；后续空闲状态 CmaFree 回到 505208 kB，VDIN faulted /
stream_error 均为 0，没有发现本轮新增的地址或资源冲突。

## KVM 回归及失败边界

| 检查 | 实际结果 |
|---|---|
| 3840×2160 H.264 | 15 秒测量、3 秒预热；59.979 fps，0 lost/dropped/freezes |
| 3840×2160 H.265 | 60.042 fps，0 lost/dropped/freezes；浏览器回调 missed=24、p99=33.5 ms，不宣称每次呈现都无抖动 |
| 音频 48k→44.1k→48k，每段15秒 | 候选及恢复基线的两段48k均通过；两者44.1k均失败，103个稳态100ms窗口中有1个测得710 Hz（输入440 Hz） |
| HID | 候选实际键盘 down/up、绝对/相对移动、点击和滚轮通过；恢复后同样通过 |
| 健康检查 | 候选加载模块 build ID 匹配、taint=0、NEW_WARNINGS=[]，One-KVM/manager active |

44.1 kHz 原始失败为 `Steady playback discontinuity, clipping or wrong pitch`；
候选 max step=0.059511，基线=0.006943。基线也失败只能排除“仅候选出现”，
不能据此证明根因、忽略候选幅度差异或宣称音频全通过。
原始日志为 `logs/display/m0/regression-window/{4k60,audio}.log`、
`logs/display/m0/baseline-audio.log`。基线对照命令同样持双锁：

```sh
python3 packaging/kernel-edge/final-regression.py run \
  --destination build/display-m0/baseline-regression --id audio
```

第一次 remaining 窗口的 manager 检查失败原因是本轮安装脚本在 runtime 登记后才
添加 tty0，触发 vim4boot 对启动参数变化的正确拒绝。脚本改为随后重新运行原有
register-runtime.py，使临时 manifest 与实际参数匹配；原失败日志保留，不改产品代码。
基线及修正后的候选 manager 完整检查均通过（内核页、PD 卡、390px 无横向溢出、
无 pageerror）；PD 卡显示本次固件 typecFallback/timeout，不宣称已取得 PD 合同。
`remaining-window-2.log` 最终输出：

```text

CANDIDATE_PHASE_PASSED remaining
BASELINE_RESTORED 3a61b75bccf8c46e9411dee92928999884bbfc7f
```
