# 2026-10-26：真实 VRR 输入与 One-KVM 连续画面

**5.15 / One-KVM 的 1080p SDR8 VRR 输入已实测通过约49–120Hz往返变频。**
H.264、H.265网页均持续显示动态内容。此结论不覆盖本地HDMI OUT、其他KVM应用、
HDR、7.3或1Hz输入；没有测量本次VRR相对固定刷新的延迟收益。
测试后已恢复原始RTK、HiDPI 4K60与H.264，没有重启或安装新二进制。
后续已[查明范围差异并修正保留字段，完成4K验证](2026-10-26-vrr-range-4k.md)；
下文保留本窗口的原始观测，旧VRRmax=60不能作为有效协议上限。

`ecaf3f20eda9aab353bf48eb3905b474a594f7696a68f2332c9424657201e08e`。
用户要求实际验证后，临时加载已有 `RTK-1080P120` 实验表，没有新增预设。

`156.0.8078.47`，1920×1080、YUV444、8-bit SDR。

Mac IORegistry的DisplayAttributes识别到48–60Hz范围，但系统设置实际提供

## 如何区分真实变频与应用更新

首轮AppKit测试虽请求48/54/57/60fps，应用实际仍约60fps，HDMI接近120Hz，
Vtotal只有1127/1128的小幅变化。因此没有据此声明宽范围VRR通过。

第二轮用独立Metal动态图：全屏CAMetalLayer、displaySyncEnabled=true、
maximumDrawableCount=2；通过 `present(_:afterMinimumDuration:)` 依次请求
120/100/80/60/54/48/120fps，每段7秒。顶部、中部、底部绘制同一帧号和校验标记。
请求帧率不等于实际输入帧率，以下只报告板端实测值。

每50ms读取一次已验证可读的 `hdmirx0/info`，每轮1000次。表中为每阶段去掉前1.5秒
及末尾0.5秒后的中位数，避免帧率统计窗口跨阶段；两轮结果一致。

| 应用请求fps | RX实测Hz | Vtotal | 基准/采集预算fps |
|---|---|---|---|
| 120 | 119.65 | 1128 | 120 / 120 |
| 100 | 105.21 | 1282 | 120 / 120 |
| 80 | 83.31 | 1620 | 120 / 120 |
| 60 | 61.85 | 2183 | 120 / 120 |
| 54 | 55.48 | 2433 | 120 / 120 |
| 48 | 49.16 | 2745 | 120 / 120 |
| 120 | 119.65 | 1128 | 120 / 120 |

Htotal保持2200、有效图像1920×1080，Vtotal随实际周期明显变化，恢复高速后又回到1128。
驱动保留实际Frame Rate变化，Capture Frame Rate使用稳定基准，符合设计。
H.264轮初段有1次VRR enabled=0的过渡采样，其余999次为1；H.265轮1000次均为1，
Base/Capture均为12000。没有把启动过渡当成完整稳态数据。

## 网页内容与连续性

使用现有latency-receiver的像素帧号和三段一致性校验，低频抽样约10次/秒。
浏览器显示屏刷新率不用于证明源端VRR；输入周期以上述RX数据为准。

| 模式 | 内容采样窗口 | 不同有效帧号 | 非法/三段不一致 | 丢包/解码丢帧/冻结 |
|---|---|---|---|---|
| H.264 | 25秒，覆盖后半段低速及回到高速 | 231 | 0 / 0 | 0 / 0 / 0 |
| H.265 | 40秒，覆盖降速及回到高速 | 382 | 0 / 0 | 0 / 0 / 0 |

H.264窗口解码1700帧，H.265窗口3108帧，均为变化负载下的总数，不是固定fps吞吐。
各窗口SSRC不变、解码关键帧计数保持1；One-KVM日志未见这些变频阶段重建采集管线。
这些证据说明测试窗口内持续收到变化内容，不能外推为所有帧绝无撕裂或长期稳定性。
MJPEG仅有前次固定4K60验证，本次未测其VRR表现，也未接入真实UU客户端。

Node直连LAN的本机权限限制仍在；HTTP经SSH转发，测试请求中的mDNS ICE候选替换为
实测en0地址，媒体走LAN UDP。未改生产ICE、hosts或网络配置。没有在采样时编译。
