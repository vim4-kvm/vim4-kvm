## V4L2 与实际码流

测试进程以 khadas 运行，停 One-KVM 后独占 `/dev/video1`；小 C 工具直接使用
MPLANE MMAP、OUTPUT CROP、STOP/drain、STREAMOFF、REQBUFS(0)。使用 720×400
可见 NV12，按协商的 raw stride/height 填充；移动条、亮度分区与边框提供逐帧内容依据。
不是 HDMI 输入性能测试。初次工具错误为重复 S_FMT 到已分配队列、误用未注册的
REPEAT_SEQ_HEADER ID；修正后重跑，未修改驱动来迁就工具。

非 streaming `v4l2-compliance -d /dev/video1`：

```text
Total for wave5-enc device /dev/video1: 46, Succeeded: 46, Failed: 0, Warnings: 0
```

| 范围 | 实测内容 |
|---|---|
| 动态 RC/PPS | AVC、HEVC 各 145 帧：2→4→2 Mbps、QP 10..40、GOP 96→48→96、slice；AVC entropy/8×8/chroma/deblock/重复头，HEVC beta/tc/constrained intra；未证明的头控制见下文 |
| 动态固定 QP | 两 codec 各 97 帧，运行中 I/P QP 及强制 IDR；静态 profile/B 控制 EBUSY，非法 bitrate=0、CPB/VBV 时长 ERANGE 后仍正常完成 |
| 多 B／分层 | 两 codec 各 B=2/3/7、分层 B=2/3/4 层、分层 P=2/3/4 层，共 18 组，每组 97 帧；逐层 QP 24/27/30/33 |
| 重复启停／部分 drain | 两 codec 同 fd 各 10 轮 19 帧、B=3；完整 drain/STREAMOFF/释放/重新设置格式 |
| GOP 中途 IDR | 两 codec 各 10 轮 71 帧，每轮两次 FORCE_KEY_FRAME，保留不满 GOP 的末尾 |
| 多实例 | 两进程同时 AVC B=3 与 HEVC 动态码率，各 10 轮 97 帧 |
| LTR | 两 codec 各 mark→use、重复 mark/use、use=0 清除 pending；B+LTR、分层 P+LTR 在 STREAMON 前后参数建立阶段 EINVAL，未产生图片 |

所有正向码流用 ffmpeg 软件解码，核对帧数、移动图案显示顺序、每轮 CAPTURE 时间戳集合、
BFRAME 标志与 ffprobe 帧型；逐帧检查不会把编码完成顺序误作显示顺序。
两组分别 86 个正向码流、6358 帧全部通过，单帧稀疏亮度采样的最大平均误差为 0.9812；
全部 CAPTURE 时间戳完整、无重复，BFRAME 数量与实际解码 B 帧数一致。

HEVC 分层 B/P 的 SPS `sps_max_sub_layers_minus1` 分别为 1/2/3，NAL
`nuh_temporal_id_plus1` 覆盖 1..2、1..3、1..4。PPS 初始 QP=26，slice delta
包含 -2/1/4/7，对应层 QP 24/27/30/33；首个 I 帧仍按独立 I QP 控制。
AVC 的 CABAC、8×8 PPS 位实际出现 0→1，固定 QP 的 slice delta 也发生变化。
未测严格目标码率收敛或长时码率精度，不能仅按控件读回宣称 RC 全部对齐。

初始候选接受运行中 AUD 0→1，但实际 AVC NAL type 9、HEVC type 35 均为零；HEVC
运行中打开重复头后也没有新增 VPS/SPS。不能凭 ioctl 成功宣称这些能力通过。
最终修正 `9d33f6ad27898` 在 legacy 固件运行中对 AUD、HEVC 重复头保持 EBUSY；
保留已观察到效果的 AVC 重复头及普通固件路径。静态控件的既有行为不变，未据本轮
实验宣称固件完全不支持它们；其静态／动态准确合同仍待后续专项。

LTR 不是仅 ioctl 成功：HEVC SPS long_term_ref_pics_present_flag=1，图片有
num_long_term_pics=1、used_by_curr_pic_lt_flag=1、相应 POC；AVC 有 MMCO 6、
long_term_frame_idx=0，以及 modification_of_pic_nums_idc=2、long_term_pic_num=0。
正常软件解码与移动内容一起证明码流实际使用了长期参考。只开放一个槽，无 B／hierarchy 组合。

此前清单“非法 LTR index 必须 ERANGE”需修正：标准整数控制由
`drivers/media/v4l2-core/v4l2-ctrls-core.c:1459` 钳制到声明范围。
FRAME_LTR_INDEX 的 min=max=0，写 1 返回成功、G_CTRL 读回 0；没有访问槽 1。
保持标准核心语义，不谎报 max=1 再在驱动内拒绝。此行为与 SDK 多槽支持无关。

## 超时与应用恢复

在真实图片编码期间，仅通过既有一次性 `timeout_command=512` 注入下一条
W5_ENC_SET_PARAM 超时；不用会让固件真实挂死的输入。旧实例收到 EIO，随后新实例正常。
冷加载后设备 isolated=0，新实例完成 97 帧编码。成功注入的内核单调时间为：

| 场景 | 超时日志→冷加载完成 |
|---|---:|
| 单独动态实例 | 347.073679→347.076305，2.626 ms |
| 与 One-KVM 并行，工具提前关闭网页 | 479.489813→479.492557，2.744 ms |
| 与 One-KVM 并行，完整重跑 | 524.807109→524.808624，1.515 ms |
| 最终组合候选，与 One-KVM 并行 | 48.751349→48.753239，1.890 ms |

测试工具最初只接受 DQBUF 的 EIO，多实例轮次实际先在 QBUF 返回 EIO，工具提前关闭
浏览器。保留失败日志并修正判定后重跑；不将这次提前关闭计作浏览器恢复成功。
重跑时 One-KVM PID 前后均为 2422，SSH 观察到设备恢复为 isolated=0 的上界为
0.746 秒；该值包含 SSH、进程退出与 sysfs 查询，不是裸硬件复位耗时。
同一网页不刷新，warmup 期间帧数恢复至 1004 后进入连续五分钟稳定采样：

```text
HEVC 3840x2160: 59.99982 fps
videoDeltas: freezes=0, dropped=0, lost=0, pli=0
pixels: 2054563583 -> 531333870
```

浏览器累计 freezeCount=1 对应 warmup 的注入恢复，不能说包含注入的整段零冻结。
稳定段 SSRC 不变，HID 实际输入检查通过；candidate-after-smoke 的 UDC configured、
taint=0，无新增 oops/WARNING。没有同时编译或软件解码干扰五分钟采样。

随后 recovery_fail_step=1 + SET_PARAM 超时进入失败隔离，journal 明确报告
`power-cycle recovery failed: -110`、`command 0x200; DMA storage retained until reboot`。
公开 sysfs isolated=1、recovering=0；内部枚举值 2 不对外暴露。第一版工具误按 2
检查布尔属性，保留失败日志后正常 reboot：28.844 秒返回默认基线与 active 服务，未卡住。
最终组合窗口重新验证失败路径：`isolated=1`、`recovering=0`，原进程 DQBUF EIO，
新 open 明确输出 `open: Input/output error`。主机含 SSH 的观察耗时 1.221 秒。
随后受控 reboot 26.885 秒回到入场 build ID 与 active 服务，shutdown 未卡住。

最终候选实时流恢复前后 One-KVM PID 均为 1433，观察上界 0.715 秒；不刷新网页后
五分钟 HEVC 4K60 为 59.99748 fps，稳定段 freeze/drop/loss/PLI 增量均为 0。
HID 键盘、绝对／相对鼠标、点击、滚轮均通过；UDC configured、taint=0。
kernel journal 无新增 BUG/Oops/WARNING/panic/Call trace，失败隔离日志为预期注入结果。

注入仅在双锁窗口内执行，工具在正在编码的图片间触发下一条 SET_PARAM：

```sh
echo 512 | sudo tee /sys/module/wave5/parameters/timeout_command
# 失败路径在下一次注入前设置；成功路径保持默认 0
echo 1 | sudo tee /sys/module/wave5/parameters/recovery_fail_step
echo 512 | sudo tee /sys/module/wave5/parameters/timeout_command
```

这些是健康固件上的超时／失败注入，不能外推为已覆盖真实硬锁的全部总线状态。
