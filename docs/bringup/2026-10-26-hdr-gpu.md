# 2026-10-26：HDR 分段测量与私有 Mali Vulkan 驱动

## 结论与范围

4K PQ Main10 当前已经使用 Wave521 硬件编码，约34–35fps的主要瓶颈是编码前的
CPU 输入复制和缓存维护。5.15 内核已有 Mali r44p0；本轮补装匹配用户态驱动，
验证实际 GPU 计算及连续 codecmm DMA-buf 导入、逐字读回。
**尚未接通视频 GPU 转换与编码器 DMA 输入，不能宣称 HDR 已达到60fps。**

## 分段测量

版本沿用[像素修复](2026-10-26-remote-hdr-pixels.md)的采集插件与 One-KVM。
Mac mini HDMI 3840×2160p60、真实 PQ、运动网格，Main10 30000kbps、目标60fps。
板端临时 SDK/插件在 `/tmp/hdr-stage`，未替换生产编码 SDK。
每组240帧，均值去掉前30帧预热；编码入口/出口使用同一进程 monotonic 时间。

| 测量边界 | 均值 |
|---|---:|
| 仅采集→CPU P010 转换吞吐 | 59.145fps |
| 仅采集时 AMLY→P010 CPU 解包 | 10.128ms |
| 完整采集→Main10 输出吞吐 | 34.651fps |
| 编码入口→输出 | 28.393ms，p95 30.038ms |
| SDK Y 平面复制及其缓存维护 | 6.350ms |
| SDK UV 平面复制及其缓存维护 | 3.990ms |
| 随后的整块输入额外 flush | 5.054ms |
| 硬件提交→中断等待返回 | 12.673ms，p95 12.852ms |

后四项属于同一次编码调用，合计约28.4ms；VMALLOC 输入路径的复制/缓存维护
约15.4ms。采集与编码通过队列重叠，不能再把 CPU 解包10ms直接加到28.4ms作为帧周期。
采集日志的 `map_sync_ms` 含缓冲池获取/背压，不能解释成纯 DMA 缓存同步时间。
硬件部分低于16.7ms只是优化依据，并不保证整条链路达到4K60。

证据：忽略目录 `build/hdr-stages/capture-only.log`、`full-profiled.log`、`probe.c`、
`results.json`。`full-instrumented.log` 未加载成功的 SDK 计时版本，不用作 SDK 分段证据。

## aml-streambox 对照与接入约束

[官方源代码](https://github.com/aml-streambox/multimedia/tree/5c272946b26060006b242e4934c2c6058514e638/libvfmcap)
使用 Mali Vulkan 将 AMLY 转成 P010，输出连续 CMA DMA-buf，再经
[编码器 DMA_TYPE](https://github.com/aml-streambox/gst-plugin-venc/blob/bc14f4f70b7acd288910caa57e5e13576fd38713/multienc-wave521/gstamlvenc_multienc.c#L2312)
送到 Wave521。我们现有 SDK 已有 P010 DMA 接口，无须增加另一个编码驱动。
[v0.4 文档](https://github.com/aml-streambox/document/blob/c6526911c9400dc210bede6bc7f410b8251dc0bb/custom-software/streambox_v0.4.md)
有59.94fps报告，也有5分钟12205帧的不同口径记录；尚未在本项目复现。

后续接入须保留以下约束：

- 我们的 AMLY 是小端 Cb,Y0,Cr,Y1，上游交换字节的 shader 不能直接使用；使用真实行宽。
- 编码器 DMA 导入取物理地址，输出须来自 `heap-codecmm`，不能换不连续 system heap。
- Vulkan 导入消费成功的 fd，须 dup 原 fd。原始采集导入持有 dma-buf 会阻止帧回收，
  每帧 GPU fence 后须释放输入导入及原 GstBuffer，不能长期缓存输入 import。
- 自有 P010 输出槽可复用；须等编码器报告对应输入退休后再写入，单凭返回编码包不足以证明退休。
- GPU release barrier、fence、输入归还与编码器输出槽生命周期须明确；双缓冲约多用50MB CMA。

离线候选 shader/语义审查位于 `build/hdr-gpu-audit/`，尚未进入生产插件。

## 私有驱动安装与验证

内核 `mali_kbase`：r44p0-01eac0，UK11.39，设备 `/dev/mali0`。
用户态库固定为
[meson_mali 51e81d36](https://github.com/aml-streambox/meson_mali/tree/51e81d36fccb1340b2dab9490da74ded29f849e1)
的 `lib/arm64/gondul/r44p0/wayland/drm/libMali_r1p0_dmaheap.so`，
与[官方 t7 配方](https://github.com/aml-streambox/meta-meson/blob/8dec0d361b225dbe5a253ab090dae7d42179e848/recipes-graphics/libgles/libgles-eabihf-gondul-wayland-drm_r44p0.bb)一致。
SHA256 `536ee80c17dc5c54e7c6ff029ca43270da8efc3fdc5b3aeb263f364419368494`。
上游标记 CLOSED；仓库不收录二进制，由固定 URL 和 SHA 下载。

复现安装（先协调板子独占，不需重启）：

```sh
python3 tools/mali-runtime.py fetch build/mali-r44p0
scp tools/mali-runtime.py build/mali-r44p0/libMali.so vim4:/tmp/
ssh vim4 'sudo -n python3 /tmp/mali-runtime.py install /tmp'
```

安装到 `/usr/lib/vim4-kvm/gpu/`，包含库、`mali.json`、来源/哈希清单。
安装器拒绝7.x、非AArch64、不匹配Mali模块及缺失依赖。
未替换系统 EGL/GLES/GBM 链接，未注册全局 ICD；显式设置
`VK_ICD_FILENAMES=/usr/lib/vim4-kvm/gpu/mali.json` 才选择它。
此步骤不会使当前 One-KVM 自动使用 GPU，未来管线需自行设置所选 ICD。
回退只需停止调用它并移除这个私有目录，不改内核及系统图形库。

ARM64 Ubuntu24.04 容器装 `libvulkan-dev glslang-tools` 后编译：

```sh
cc -O2 -std=c11 -Wall -Wextra -Werror tools/mali-dma-probe.c -lvulkan -o mali-dma-probe
glslangValidator -V tools/mali-dma-probe.comp -o mali-dma-probe.spv
spirv-val mali-dma-probe.spv
```

二进制和 shader 复制到板上后：

```sh
VK_ICD_FILENAMES=/usr/lib/vim4-kvm/gpu/mali.json ./mali-dma-probe mali-dma-probe.spv
```

真实识别 Mali-G52、Vulkan1.3.231，驱动44.0.0；创建 compute device/pipeline 成功。
分配一帧4K P010容量24,883,200字节的 `heap-codecmm` DMA-buf，导入为 storage buffer；
GPU 写入索引相关模式，fence完成并转移所有权后 CPU 逐一核对6,220,800个uint。
首次通过，随后无截图/编码占用时连续十次全部通过，提交加等待约3.9–4.2ms；
这是简单填充任务，**不能当作 AMLY 转换耗时或视频帧率**。
结束后 dma-buf 列表仅保留原 DRM heap-gfx 对象，无残留 codecmm 导入。
一次与 MCP 截图编码启动重叠的分配失败，codec CMA 日志明确报碎片；该轮不计作通过。
说明视频与 GPU 并发时的 CMA 分配次序/预算仍须完整管线验证。
日志在 `build/hdr-gpu/installed-validation.log`、`repeated-dma-validation.log`、
`repeated-dma-after-idle.log`。

## 失败 CMA 候选撤回

`common_drivers a321ceb5` 整块主采集池候选复测 PQ→SDR 后仍无法申请200MiB，
不能将它作为已修复方案；`6558c1ee` 已 revert。
恢复 `/var/backups/vim4-hdr-remote-20261026/before-cma.tgz` 中模块、initrd、资格表并重启。
当前 aml_media SHA `8b300e74f40028c1f4459c3fb76299cfcab4888a06aeb4c56e3141232884a0f4`，
加载 note `e013aee8a40997eb849002a857ceab9fedb60e6739c2ecd2d43ff51689debd3e`，
initrd `23ec95261f7430b2ce4fab1293582978f96339ab4e53c4aaacafbfa20a2a2b07`，
boot ID `f3998de9-e7e1-4d02-8a06-7e5ae829a076`，One-KVM 与 HDMI 服务已恢复。
失败证据：`build/hdr-stages/cma-transition-failure.log`、`input-transition-cma.log`。
原先花屏修复和 SDR 自动选择保留；源端 HDR/SDR 往返分配问题仍未解决。

恢复本轮开始时源端的 HDR 开启状态后，旧模块也再次触发编码器200MiB分配失败，
日志 `build/hdr-gpu/source-hdr-switch-cma.log`；首次 `video-smoke.log` 超时，不计作通过。
再次重启恢复，最终 boot ID `5c6b0cb6-2523-43fe-a4a4-c2cbdb0850f5`，私有GPU库哈希保持一致。
最终输入为4K60 PQ，输出恢复 H.264、原尺寸/自动帧率、HDR转换开启、quality80。
网页实测60.075fps，20个推进标记、三处帧号一致，无无效标记，测量窗口未增加解码丢帧；
见 `build/hdr-gpu/video-smoke-after-reboot.log` 与 `video-smoke.json`。
该视频验收使用原八位硬件管线，没有并行运行GPU探针。
内核 taint 仍为既有12800，未发现新增Oops/BUG；未测试音频、UU官方客户端和HDMI OUT。
