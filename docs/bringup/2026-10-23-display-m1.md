## 根因、修复与同类路径审查

RMFB/文件关闭复制旧 plane state，再把 `fb`、`crtc` 置 NULL。
原 `plane_check` 遇到 `!new->crtc` 提前成功返回，跳过了标准 helper 对 `visible`
的清理。旧 `visible=true` 留下；CRTC 仍 active 时 flush 根据它对 NULL fb 求 DMA 地址。
这是软件生命周期错误，与寄存器共享或 PLL 无关。

`c1315a9` 让所有新 plane state 都执行 `drm_atomic_helper_check_plane_state()`；
解绑时传 NULL CRTC state，由 helper 清掉 visibility，再退出格式/地址检查。
flush 进入保留固件帧路径，等待两次实际 IRQ 后释放旧扫描帧。
测试直接抽取驱动真实 check/flush/scanout/IRQ C 函数，用受控 IRQ 和 DRM helper
合同 mock 重现 active CRTC + NULL fb/crtc + copied visible=true：旧代码断言失败，
修复后通过，并验证旧 buffer 退休及地址回到保留帧。

同类路径离线审查：格式/GEM 地址检查位于 helper 成功且 visible 后；CRTC check
将 affected plane 纳入事务；flush 的旧/新 CRTC state 来自有效 atomic 事务；disable
显式切回保留帧；IRQ 不访问 plane fb；超时后的 scanout/stalled 持有引用。
bridge mode 分配已有 NULL 检查，handoff 不进入普通 TX/audio 回调；shutdown 仅由
成功绑定的内建 platform driver 调用。未发现另一处相同 NULL 生命周期缺陷。
这不替代真实 DRM RMFB 压测或板上关闭/disable 验证。
