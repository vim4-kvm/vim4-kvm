# 2026-10-19：7.3 Wave521 硬编码与 4K60

摘要：实验接收路径已取得 3840×2160p60 RGB24/NV12，Wave521c 已编码真实 HDMI
运动画面的 H.264、H.265。两种格式各 1800 帧解码后，三处帧号及红绿蓝色块通过。
这是固定 RGB8 输入的驱动实验，不是现有 KVM 应用迁移完成或全功能内核验收。

## 硬件与配置

- VIM4/A311D2，新版板；实验 release `7.3.0-rc7-vim4kvm-uhd1+`。
- 只在 hdmirx-test DTB 接入 `amlogic,t7-wave521c`；普通 VIM4 DTB 不增加编码节点。
- 编码寄存器 `0xfe310000`，实际产品号 `0x521c`，固件 revision `214414`。
- Wave A/B/C 均为约 666.7 MHz，未超频。4K VPU/CLKB 约 666.7 MHz，VAPB 500 MHz。
- 实验启动项 `cma=512M@0x10000000-0xf0000000`，固件与 DMA 地址限制在 4 GiB 以下。
  GStreamer 探测 8K 上限后保留 32 MiB 码流缓冲，256 MiB CMA 曾不足并产生分配告警；
  没有通过缩小有效的 sizeimage 请求绕过问题。
- 默认启动项及 Stock 均保留；实验服务屏蔽策略沿用前一轮，不启动 KVM 应用。

接收端实际测得 3840×2160、4400×2250 总时序、约 594 MHz TMDS；物理线频约
148.5 MHz，SCDC 1:40。测试源为 Mac 物理 HDMI 桌面的
`latency-source.swift --motion --verify-coherence`，不是虚拟显示器。

## 修正

RX 使用 256 字节 RGB8 CTA EDID，并在 4K 路径接入 SCDC。HDMI 前导码阈值为 6，
原先无 CTA 的 DVI 1080p 路径保留 0；仅 PLL/对齐成功不能证明视频时序正确。
DFE 使能位属于 DCHD0 bit 27，复位属于 DCHD2 bit 26。

VDIN 增加固定 4K 几何与单分配 NV12，使用有限范围 BT.709 矩阵。物理行 FIFO
仍为 `0x780`，不能随输入宽度改为 3840；错误的 FIFO 深度曾导致横向破损。
NV12 路径必须保留公共输入使能 bit 4。颜色块另揭示了 RGB 分量顺序错误，
现在 RGB24 与 NV12 分别通过颜色检查。DMA 仍写入驱动私有 cached 环，再复制到
vb2 导出缓冲；尚非从采集硬件到编码器全程零复制。

Wave5 适配旧固件的能力掩码、总线空闲值、复位及电源管理。
共享 DMA-buf 的色度平面有非零偏移；驱动现在检查分配及有效载荷边界，硬件地址
加入 data_offset。GStreamer 1.24.2 的 V4L2 allocator 在 QBUF 时把 bytesused
重算为不含偏移的大小，需使用仓库中的小补丁。

1080p 额外分开有效载荷与分配容量：NV12 仍紧密排列，但 vb2 尾部预留 1088 行的
编码容量。Wave5 的源容量按 16 行对齐，编码可见高度仍为 1080；平面视图保留
真实 UV 地址，仅未使用的尾部容量允许重叠。没有移动有效像素，也没有绕过
编码器的范围检查。两种格式各 180 帧的 1080p 编码及解码颜色检查通过。

## 固件与复现依赖

T7 固件不在本仓库分发；现有 `chagall.h` 许可有限制，不能把二进制或头文件
加入公开仓库。需要单独合法取得匹配头文件，再本地转换：

```sh
python3 packaging/kernel-edge/prepare-wave521c-firmware.py /path/to/chagall.h build/t7-wave521c-enc.bin
xxd -r -p packaging/kernel-edge/uhd60-edid.hex > build/uhd60-edid.bin
```

转换工具只接受实测版本，输出必须不存在。固件 952192 字节，SHA-256
`873103d7520d5cad737cfe4458a2891c065d566ff556a47ab735e60f27acf031`；
EDID 256 字节，SHA-256
`3164c2cac27317bfcb698292c3a3f4f12e57ca8f9002619e96fe19e5ccf477c1`。
板上对应 `/lib/firmware/amlogic/t7-wave521c-enc.bin` 和
`/lib/firmware/vim4-hdmirx-ddc-test/uhd60-edid.bin`。

GStreamer 使用官方 `gst-plugins-good-1.24.2.tar.xz`，SHA-256
`6e347c72d4b8b2886d890ffe9f6767a9edb02f201588e8c3a572dcd08d9852bd`。
在解压目录应用 `packaging/kernel-edge/gstreamer-v4l2-offset.patch`，再执行：

```sh
meson setup ../gst-build . -Dauto_features=disabled -Dv4l2=enabled -Dexamples=disabled -Dtests=disabled -Dnls=disabled
ninja -C ../gst-build
```

依赖 GStreamer 开发包、Meson、Ninja、gudev/v4l2 开发包。插件仅通过测试进程的
`GST_PLUGIN_PATH` 选择，不覆盖系统插件；设备节点变化时使用新的 `GST_REGISTRY`。
测试脚本用 appsink/appsrc 为同一导出分配建立两个平面视图，并持有父缓冲，
防止编码结束前归还采集队列。没有增加用户态像素复制。

## 测量边界与记录

原始 RGB24/NV12 快照均通过三处帧号和颜色检查。
NV12 三轮各 600 帧的 DMA-buf、缓冲耗尽恢复、持有期间不变、REQBUFS(0) 孤儿
缓冲重映射及带流关闭通过；排除前 60 帧后各约 59.998 fps。
日志为 `logs/kernel-edge/uhd1-nv12-reload-stream.log`。

一次更长的原始流检查在第 2576 帧因源帧号重复失败；同一时段源端绘制日志有
超过一帧的间隔，尚不能据此归因于驱动。没有将该次算作 5400 帧通过，也没有
放宽检查器。三处标记一致、捕获序号及时间戳递进与源端内容推进分别检查。

早期两种编码各 1800 帧的稳定段均为 59.998 fps，全部解码检查通过，证据为
`uhd1-soak-h264.log`、`uhd1-soak-h265.log` 与 `uhd1-vm-soak-*-verify.json`。
早期配置虽设置 bitrate，但未启用 frame rate control，不能用于证明目标码率。
后续已显式开启帧及块级码率控制，需以最终记录评价码率与性能。

显式开启码率控制、20 Mbps、GOP 60、各 1800 帧后的记录如下。前 60 帧不计入
稳定段帧率和 pad 耗时；整机 CPU 统计包含整个测试及启动阶段。

| 4K60 格式 | 稳定 fps | 整机 CPU | pad p50 / p99 | 容器平均码率 |
|---|---:|---:|---:|---:|
| H.264 | 59.998 | 8.12% | 13.77 / 24.50 ms | 20.15 Mbps |
| H.265 | 59.998 | 8.24% | 14.79 / 36.65 ms | 20.01 Mbps |

见 `uhd1-final-rc-h264.log`、`uhd1-final-rc-h265.log` 和
`uhd1-final-rc-verify.json`，全部 3600 帧的运动标记和颜色检查通过。
修正设备树后又分别编码/解码 180 帧真实 4K 输入，并在两次编码后卸载、重载
Wave5，见 `uhd1-no-bridge-live.log` 和 `uhd1-no-bridge-verify.json`。

板上 ffmpeg 软件解码和 Python 校验曾分别占约 274% / 85% 单核 CPU，已停止并
迁到构建 VM。编码阶段单独读取整机 `/proc/stat`；这包括驱动线程、中断和复制，
不能只用编码进程的 user/sys 时间代表整机开销。pad 耗时端点是采集出口至解析后
access unit，既不是纯硬件时间，也不是光学或浏览器端到端延迟。

## 恢复及未覆盖范围

早期 Wave5 卸载曾导致 SSH、串口、SysRq 均失去响应，用户 RESET 后恢复 5.15。
根因之一是错误地把 `RESET_BRG_NIC3_WAVE` 交给编码器驱动；它是 NIC3 AXI 桥，
不属于编码 IP 的复位。仅保持电源域也不能解决重载超时。最终设备树移除该项，
binding 明确拒绝 T7 的 resets 属性；由安全电源控制器管理桥，Wave5 使用内部
软件复位停止 DMA。H.264/H.265 合成输入和真实 4K 输入编码后的重载均通过，
卸载后 A/B/C 时钟引用归零，DOS_WAVE 域关闭；最终测试内核 taint 为 0。
诊断模块仅在此前独立启动中加载，未安装到发布模块目录。
VDIN 若无法确认 DMA idle，继续保留缓冲与模块直到重启，不强制卸载。

旧固件的 HEVC 码流仍标记 Level 5.0，即使请求 5.1；H.264 实际为 Level 5.2。
HEVC 已解码 4K60 不代表其 Level 标记符合 4K60 约束，仍需解决固件/码流兼容性。
5.15 的同一固件路径也输出 HEVC Level 5.0，因此这不是本轮新出现的回归。

## 5.15 参考对照

回到默认 5.15 后，暂时停止 One-KVM/管理器，保留 HDMI 服务及 RTK 4K60 输入，
使用 One-KVM 相同的私有插件路径运行 `vfmcapsrc ! amlvenc`。同样设为 20 Mbps、
GOP 60、关闭逐行刷新，分别输出 1800 帧，再恢复服务。

| 5.15 格式 | 稳定 fps | 整机 CPU | pad p50 / p99 |
|---|---:|---:|---:|
| H.264 High | 59.998 | 1.02% | 11.84 / 14.32 ms |
| H.265 Main | 59.998 | 0.72% | 12.98 / 16.52 ms |

证据 `uhd1-stock-h264-private.log`、`uhd1-stock-h265.log`、`uhd1-stock-metadata.log`。
旧链路 performance governor，big/little 记录为 2208/2016 MHz；新链路这轮未记录
CPU 频率。新 H.264 为 Constrained Baseline，旧为 High；新测试还有 Python
平面桥及私有环 CPU 复制，旧链路为 C 插件直接导入。因此只能确认当前测试的
吞吐均达 60 fps，CPU 和 pad 时间仍有差距，不能宣称性能/画质已完全对齐。
下一轮应分别排除测试桥开销、核对频率，并优化采集复制。

测试结束恢复默认 `5.15.137-vim4kvm`，One-KVM、管理器、HDMI、USB gadget 和
PD 服务均 active，dpkg audit 无残留。开发依赖安装曾触发 initramfs 更新因
/boot 空间不足失败；备份后暂存实验 Image、完成配置再恢复 Image，最终配置正常。

本轮没有把新内核设为默认，也没有替换应用的 vfmcapsrc/amlvenc 接口。HDR、深色、
YCbCr 输入、音频、任意分辨率协商、热插拔全链路、网页观看与低延迟逐行刷新，
以及和 5.15 相同设置的 CPU/延迟/画质对照，均不能由本次固定模式实验代替。

## 恢复后复核：5.15 编码锁权限

2026-10-20 UTC 的网页复核发现 One-KVM 启动 4K H.264 时 SIGSEGV，systemd 已自动
重启 5 次；服务 active 和 HTTP 可访问并不能证明视频正常。HDMI 仍锁定 NV21
3840×2160、约 59.98 Hz，独立 vfmcapsrc 取帧正常，最小 amlvenc 管线同样崩溃。

strace 显示 `/tmp/vpu_mutex.map` 的 `open(O_RDWR|O_CREAT)` 返回 EACCES，紧接着
访问地址 `0x10` 崩溃。文件属主 root:root、权限 755，时间与 root 编码对照测试
吻合；khadas 无法写入，厂商编码库未安全处理初始化失败。仅将原文件属主修正为
khadas:khadas，保留 inode、内容和锁状态，不删除或重新初始化共享锁，即恢复编码。
本次恢复不需要回退系统库或修改内核、EDID。

修复后最小 H.264 管线正常完成 60 帧并 EOS；通过 SSH 转发访问应用本地后端，
Chrome WebRTC 连续 15 秒解码 904 帧 3840×2160 H.264，约 60.24 fps，丢帧及丢包
增量均为 0。应用 PID 4000、重启计数 5 均未变化，USB 状态 configured。
本次没有注入键鼠或验证音频，也没有测运动画面或端到端延迟。
证据：`logs/kernel-edge/uhd1-stock-lock-eacces.strace`、
`logs/kernel-edge/uhd1-stock-lock-recovery-browser.json`。

后续 5.15 厂商编码对照须用应用相同的 khadas 用户；7.3 V4L2 实验的 root 权限
需求不能直接沿用到旧编码库。恢复检查须实际打开视频，不能只检查服务运行状态。
