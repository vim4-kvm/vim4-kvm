# 1080p120 完整链路审查

2026-10-26，纯源码/既有证据审查，未访问板子、修改配置或执行硬件测试。
基线：主仓 `797f018`、common_drivers `f3b34664e`、gst-plugin-venc `89a5b01`、
One-KVM `b6b8057c`。7.3 接收范围核对发布锁 `b1300eb808f4`，另只读 VM
`linux-7.3@c24465df1dd7` 的实现；后者不代表当前安装内核。

结论：1080p120 有可实施路径，但目前不能称完整支持。至少有厂商 RX 格式选择、
One-KVM/UU 帧率上限、7.3 公共采集插件固定60fps、PiKVM配置和测试源节拍需要处理。
应先实现 **1080p120 SDR 输入→原始采集→One-KVM H.264/H.265→接收端**，
再扩展其他应用和本地 TX。TX 的60Hz限制不是远程采集的必要前置；VRR另作专项。

## 时间戳、编码质量与客户端

One-KVM [video_track.rs](../One-KVM/src/webrtc/video_track.rs):161起以实际PTS推进
90kHz RTP时钟，另有`90000/config.fps`回退；120整数率是750ticks，分数率需用真实PTS，
不要把重复帧或错误时间戳当120输出。输入状态当前多处把分数率四舍五入，首轮可限定
精确120，随后必须补120000/1001（约119.88）的长测，记录PTS与接收端漂移。

One-KVM H.264协商等待实际SPS信息（webrtc_streamer.rs:729），应继续据真实码流确定
profile/level；NanoKVM的client.go:15仍有固定`profile-level-id=4d001f`，高刷验证时要核对
实际SPS与SDP/客户端能力，不以“浏览器偶尔能播”掩盖不一致。本次没有确认客户端的
硬件解码能力上限，UU实际请求参数也尚未测量。

120fps每帧时间预算为8.33ms；相同码率下每帧字节预算约减半，需要固定码率和固定
质量两个对照。1080p120像素吞吐低于4K60只能说明值得试，不能代替编码吞吐实测。
行刷新周期、重连/PLI恢复和发送队列也需复核；不要为维持吞吐引入B帧重排。
当前One-KVM的MJPEG硬件上限仍单独按60处理，软件JPEG为10，应保留这些能力边界。

## 分阶段实施

1. **测试工具与离线回归。** 当前[latency-source.swift](../tools/latency-source.swift):197
   用1/60 Timer，即使HDMI切120也不能产生120个独立内容帧。新增按目标显示节拍驱动的
   可选120测试源并记录真实绘制/显示时间，继续使用三处帧号校验。先覆盖RX格式映射、
   EDID校验和默认回退、60/120与分数率caps、平台能力上限、UU请求夹取、停止重开。
2. **5.15原始采集。** 私有候选补RX映射，临时EDID选择1080p120 SDR8，保留现有HDR双路径
   与完整帧语义。先不启动编码，用V4L2逐帧sequence/timestamp加动态内容证明120个不同帧。
   HDMI服务不应随浏览器重连重启。记录VDIN0/VDIN1分别的实际推进。
3. **编码与One-KVM。** 固定源分别测H.264/H.265硬编码，随后候选放开1080p上限和UI/UU
   设置路径；裸码流、LAN浏览器、真实UU客户端逐层验证。初始只支持已验1080p模式，4K仍60。
4. **7.3与其他应用。** 7.3先验证现有接收范围，再修公共插件的固定60caps；逐应用重复
   输入/输出/恢复验证。7.3正式安装与候选源码区别沿用[内核记录](subsystems/kernel.md)。
   Nano、Jet、Pi的JPEG不得用H26x结果替代；按真实瓶颈决定是否开放120。
5. **HDMI OUT。** 在真实支持1080p120的sink上修TX准入与模式选择；保留无sink和60Hz sink
   的远程120采集。输出固定120先验收，VRR由独立方案推进，不把二者绑定成一次大改动。

## 可复现验收矩阵

所有硬件窗口先协调并持有board/heavy双锁；不能与VBV或其他编码测试并行。
用户此前的一次临时内核切换授权不自动扩展为本专项的任意重启；需要启动候选时按
[工具目录](tools.md)处理。记录实际内核/模块、插件/库、浏览器/UU版本、码率、温度和时钟。

| 窗口 | 控制项 | 通过证据 |
|---|---|---|
| 原始采集 | 1080p60→120→60；SDR8；有/无OUT | 实际RX时序正确；连续有效sequence，原始三处帧号一致且独立推进；重复帧、缺帧、ERROR分别计数 |
| 硬编码 | H.264/H.265；固定录制输入；静态文字/运动/场景切换；60/120同码率及等质量对照 | 完整解码、实际SPS、帧数和顺序；编码入口→输出p50/p95/p99；编码吞吐与真实呈现分开报告 |
| LAN浏览器 | One-KVM先行；接收显示器确认≥120Hz；同一固定客户端 | 发送AU、收包、解码、浏览器呈现及内容帧号分别约120；零新增freeze且丢失/重复有明细；不能用60Hz屏幕验证120呈现 |
| UU | 官方客户端独立会话；记录客户端请求和实际采用fps | 确认请求没有被夹到60；真实解码/显示与输入响应测量；网页统计不能代替UU结果 |
| 稳定性 | 初筛30秒后≥10分钟；60↔120反复10轮；重连、PLI、源休眠/恢复 | 无DMA/CMA累积、无新内核告警、无旧帧持续输出；服务恢复后模式/设置正确 |
| 分数率 | 119.88与120分别；至少10分钟 | 实际PTS/RTP推进，音画偏差首尾变化；不把caps整数120当真实采样周期 |
| 本地透传 | 支持120的sink/仅60的sink/无sink；KVM同时运行 | 实际TX输出读回和物理内容验证；远程采集不中断；不由TX时钟推断光学延迟 |

本轮仅形成实施方案，尚无1080p120实板成功证据，也没有修改任何生产源码。
